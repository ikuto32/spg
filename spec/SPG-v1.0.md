## 1. 概要

SPG は、棋譜と定跡を同じ「局面グラフ」として格納する、エンジン・大規模処理向けのフォーマットである。バイナリ（.spg）を正本とし、差分確認や手編集のために、論理データを表すテキスト表現（.spgt）を定める。最大1兆局面を扱うことを想定する。

設計目標は次の4つである。

1. **エンジンが速く引ける**：局面キーで二分探索でき、mmap したまま使える固定長レコード。最大1兆局面を想定し、添字とオフセットはすべて64bit。
2. **棋譜と定跡を1つのモデルで扱う**：棋譜は局面グラフ上の「経路の木」、定跡はグラフそのもの。棋譜集から定跡を作る、局面から棋譜を逆引きする、が変換なしでできる。
3. **既存形式から無損失で取り込める**：10章に挙げた形式と記法について、情報を落とさない。表せない要素を含む入力は、取り込みを失敗させるか、欠けた部分を報告する。逆方向は表現できる範囲で行う。
4. **意味が仕様で決まっている**：評価値の視点・単位、文字コード、整列の有無などを、実装ではなく仕様で規定する。

この文書は SPG v1.0 の仕様書であり、参照実装と適合テスト用のデータ集は範囲外とする（計画は付録C）。作者とライセンスの表示は 7.13 と 8.3 で定める。

**版の状態**：この仕様は 2026年11月6日に v1.0（メジャーバージョン 1、マイナーバージョン 0）として凍結した。以後、v1.0 の規範的な内容は変更しない。誤りの訂正は正誤表として公開し、機能の追加と変更は 12章の規則に従って新しいマイナーバージョンまたはメジャーバージョンとして行う。

## 2. 規範的記述の読み方と用語

### 2.1 要件のキーワード

この文書のキーワード「MUST」「MUST NOT」「REQUIRED」「SHALL」「SHALL NOT」「SHOULD」「SHOULD NOT」「RECOMMENDED」「NOT RECOMMENDED」「MAY」「OPTIONAL」は、BCP 14（RFC 2119、RFC 8174）に記述されているとおりに解釈する。ただし、ここに示すようにすべて大文字で書かれた場合に限る。

本文は日本語で書き、要件を表す述語の直後に括弧でキーワードを併記する。キーワードを伴わない日本語の述語は要件を定めない。この文書では SHALL と SHALL NOT は使わない。

| 本文の表記 | キーワード |
| --- | --- |
| 〜しなければならない、必須である | MUST、REQUIRED |
| 〜してはならない | MUST NOT |
| 〜すべきである、推奨する | SHOULD、RECOMMENDED |
| 〜すべきではない | SHOULD NOT、NOT RECOMMENDED |
| 〜してもよい、任意である | MAY、OPTIONAL |

### 2.4 共通の規則

1. 多バイト整数は、別段の定めがない限り、リトルエンディアンで格納しなければならない（MUST）。符号付き整数は2の補数で表す。
2. 予約と記した欄・ビット、および定義されていないフラグのビットには、書き手は 0 を書かなければならない（MUST）。読み手は、自身が知っているマイナーバージョン以下のファイルでそれらが 0 でないとき、そのデータを破損として扱わなければならない（MUST）。それより新しいマイナーバージョンのファイルでは、読み手は予約の欄と未定義のフラグのビットを無視しなければならない（MUST）。予約領域の一覧と、後の版で使うときの規則は 7.9 で定める。
3. 「拒否する」とは、読み手がそのファイル（マニフェストで束ねたファイル群ではその全体）を使わず、エラーとして報告することをいう。
4. 「破損として扱う」とは、読み手が該当するブロックに含まれるレコードを使わず、エラーとして報告することをいう。エンジンは、破損として扱った局面を「定跡にない」ものとして扱わなければならない（MUST）。
5. 「全ビット 1」は、その欄の幅のすべてのビットが 1 の値をいう。全ビット 1 を「なし」と定めた欄では、それ以外の値が有効な参照でなければならない（MUST）。

## 3. 背景：既存形式の課題（参考）

この章は、SPG が解決しようとする既存形式の課題をまとめる。要件は定めない。

### 3.1 棋譜形式の課題

棋譜形式の問題は、仕様が実装に埋もれていること、形式ごとに持てる情報が違うこと、拡張の置き場がコメント欄しかないことの3点に集約される。

| 形式 | 主な課題 |
| --- | --- |
| KIF | 分岐・任意局面の書き方が文書化されていない。「王/玉」や空白数などの方言。持ち時間欄が自由文字列。手番・取った駒を持たない |
| KI2 | 移動元がなく相対表記からの逆算が必要。消費時間なし。▲△/▽、全角/半角の揺れ |
| CSA | 分岐を書けない。文字コード規定が V2.2（環境依存）と V3.0（宣言なしなら SHIFT\_JIS）で食い違って見える |
| SFEN/USI | メタ情報を持てない。`position` / `sfen` 接頭辞の有無、終局理由（`resign` 等）が一部ソフトのみ |
| JKF | 「しおり」相当がない。統一を狙ったが選択肢が1つ増えた形 |
| 思考コメント | Floodgate/CSA V3、ShogiGUI、ShogiHome、ぴよ将棋で記法が別々。読み筋の手の表記も CSA・KIF・KI2 に分かれ、評価値の視点・単位が明記されない |

形式をまたいだ課題は次のとおりである。

- **往復変換で情報が落ちる**：分岐、消費時間、メタ情報、しおりのどれかが必ずどこかで欠ける。
- **文字コードを推定しないと読めない**：拡張子 .kif で中身が UTF-8 のファイルが実在する。
- **人間用と機械用の情報が同じ欄に混在する**：別アプリで編集すると思考データが壊れる。
- **寛容な読み込みが方言を温存する**：出力側を正す圧力が働かない。

出典：[将棋の棋譜や局面のフォーマット（Qiita, sunfish-shogi）](https://qiita.com/sunfish-shogi/items/964e139ef3bfd8f738d4)、[json-kifu-format](https://github.com/na2hiro/json-kifu-format)、[81Dojo .kif format](https://system.81dojo.com/ja/topics/522)

### 3.2 定跡形式の課題

定跡形式の問題は、局面の識別方法が形式ごとに違うことと、各列の意味が実装と慣習で決まっていることである。

| 形式 | 局面の識別 | 主な課題 |
| --- | --- | --- |
| ShogiGUI（.sbk） | 不明 | 仕様非公開。変換ツール BookConv のソースが事実上の仕様 |
| やねうら王定跡2016（.db） | SFEN 文字列（手数付き） | テキストで起動時の読み込みが遅い。整列済みかを示すヘッダがない。途中の列を省略する書き方が未規定。同一 SFEN の重複時の挙動が未検証 |
| Apery 定跡 | 64bit ゾブリストハッシュ | ハッシュ衝突で別局面と混同しうる。ハッシュから局面を復元できない。ハッシュ表がソフトごとに違えば互換性がない |
| 技巧定跡 | 64bit ゾブリストハッシュ | Apery と構造はほぼ同じだが各エントリの内容が違い、相互に読めない |

具体的に起きている問題は次のとおりである。

- **ハッシュキーは移植性がない**：やねうら王の作者は、ソフトを作り変えると同じ局面でもハッシュ値が変わりうるため、ハッシュキーを定跡のキーにする方式は廃れると見ている。衝突対策として手数を併記する方法もあるが、手数が違う同一局面（角換わりの手順前後など）を別扱いしてしまう。
- **列の意味が慣習で揺れる**：やねうら大定跡では、出現頻度の列にエンジンのバージョン番号を100倍した値を入れる運用がとられた。
- **「未入力」と「0」を区別できない**：ShogiHome が途中の列を空にして出力したところ、やねうら王と BookConv は連続する空白を1つの区切りとして読んだ。結局 `none` を書く方針になったが、これは2025年のコメント欄でのやり取りで決まったものである。
- **変換で情報が落ちる**：BookConv で技巧定跡から ShogiGUI 定跡へ変換すると、評価値などが失われる。
- **評価値の意味が揃わない**：やねうら王形式は歩を100点とする手番側の視点だが、他形式は各エンジンの尺度のままである。
- **棋譜と定跡が別世界**：棋譜から定跡を作るたびに SFEN 経由の変換が必要で、定跡の局面から元の棋譜をたどる手段がない。

出典：[将棋ソフト用の標準定跡ファイルフォーマットの提案（やねうら王公式サイト）](https://yaneuraou.yaneu.com/2016/02/05/standard-shogi-book-format/)、[BookConv](https://github.com/ai5/BookConv)、[将棋の棋譜や局面のフォーマット（Qiita）](https://qiita.com/sunfish-shogi/items/964e139ef3bfd8f738d4)

## 4. 設計原則（参考）

上の課題から、次の9つを設計原則とする。この章は参考（非規範）であり、各原則は規範的な章の要件として具体化されている。各行の右列は、その原則で解消する課題である。

| # | 原則 | 解消する課題 |
| --- | --- | --- |
| P1 | 局面は手数を含まない正準符号（CPE, 256bit）で識別し、ファイルに必ず格納する。索引には仕様で固定したハッシュを使い、照合は CPE で行う | ハッシュ衝突、局面を復元できない、ソフトごとにハッシュが違う、手順前後の同一局面 |
| P2 | 「局面グラフ」と「棋譜の木」を分ける。グラフは局面単位の集計、木は対局固有の情報（消費時間・コメント）を持つ | 棋譜と定跡が別世界、合流で消費時間が混ざる |
| P3 | 固定長レコードと整列済み索引を必須にし、mmap したまま二分探索できる。添字は64bitとし、最大1兆局面をキー範囲で分割したファイル群として扱える | テキスト定跡の読み込み時間、整列の有無が不明 |
| P4 | 評価値は視点・単位・エンジンを必ず明示する | 評価値の意味が揃わない |
| P5 | 値の「なし」を数値と区別して表現する | 「未入力」と「0」の混同 |
| P6 | 人間のコメントと機械向け注釈を別の欄に置く。注釈は名前空間付きの型付きキー | コメント欄の多重利用、思考コメントの方言 |
| P7 | 文字列は UTF-8 のみ。推定はしない | 文字コードの推定 |
| P8 | 未知のセクションと注釈は読み飛ばし、書き戻すときは保持する | 拡張のたびに方言が分岐する、変換で情報が落ちる |
| P9 | 破損は64 KiB のブロック単位で検出して局所化し、索引は原データから作り直せるようにする。改ざんは暗号学的ハッシュと署名という別の層で守る | ビット反転、更新時の世代の混在、配布物の改ざん |

あわせて、次の2点を範囲外とする。

- 局面の左右反転・先後反転による同一視はしない（やねうら王形式と同じ判断）。必要なら索引の外で行う。
- 千日手の判定に必要な手順の履歴は局面グラフに持たない。グラフのエッジは履歴に依存しない情報だけを持ち、千日手の扱いはエンジンに任せる。

## 5. データモデル（参考）

SPG は「局面グラフ」と「棋譜の木」の2層からなり、両者は局面キーで結びつく。消費時間やその対局のコメントのように対局に固有の情報は木に、評価値や勝敗統計のように局面に固有の情報はグラフに置く。

- **局面ノード（POSN）**：手数を含まない局面。手順前後で同じ局面になれば1つに合流する。
- **指し手エッジ（EDGE）**：局面から局面への指し手。定跡の候補手そのもので、重み・評価値・勝敗統計を持つ。
- **棋譜（RECS）と棋譜ノード（RNOD）**：開始局面を根とし、分岐を含む指し手の木。ノードは局面を直接持たず、根からの手順で局面が決まる。
- **注釈（ANNO）**：上のどれにでも付けられる型付きの キー＝値（コメント、しおりなど）。評価値・深さ・読み筋は、1回の思考ごとに束ねた解析結果（ANLS）として同じ対象に付ける。
- **権利情報（RGHT）**：作者・編者・提供元とライセンス（SPDX のライセンス式）。注釈 rights でファイル全体・棋譜・ノード・局面・エッジのほか、個々の注釈・解析結果・出典にも付け、付いていないデータは上位の権利情報を受け継ぐ。
- **出典と由来情報（SRCS・PROV）**：複数の定跡や棋譜集を統合したとき、どの出典がどの局面・エッジにどんな値で寄与したかを保つ任意の表。統合後も出典ごとの権利情報と値をたどれる。

## 6. 基本符号化

局面は手数を含まない256bitの正準局面符号（CPE）で、指し手は16bitの Move16 で表す。局面の索引キーは CPE の XXH3-64 とする。

### 6.1 升番号・駒種コード・標準一式

升番号は `sq = (筋 − 1) × 9 + (段 − 1)` とする。１一 = 0、１九 = 8、２一 = 9、９九 = 80 である。

| 駒種 | 歩 | 香 | 桂 | 銀 | 金 | 角 | 飛 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 駒種コード | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
| 標準一式の枚数 | 18 | 4 | 4 | 4 | 4 | 2 | 2 |

「標準一式」は、上の表の38枚と先後の玉各1枚である。枚数を数えるとき、成駒は元の駒種として数える。

### 6.2 指し手（Move16）

| ビット | 内容 |
| --- | --- |
| 0–6 | 移動先 `to` |
| 7–13 | 移動元 `from`。0–80 は盤上の升、81–87 は駒打ち（81 ＋ 駒種コード） |
| 14 | 成り |
| 15 | 予約 |

`0x0000` は「指し手なし」を表す特別な値である。それ以外の Move16 について、書き手は次の条件をすべて満たすものだけを書かなければならない（MUST）。読み手は、条件を満たさない Move16 を破損として扱わなければならない（MUST）。

1. `to` は 80 以下である。
2. `from` は 87 以下である。
3. `from` が 80 以下のとき、`from` と `to` は異なる。
4. `from` が 81 以上（駒打ち）のとき、成りビットは 0 である。

書き手は、投了や中断などの終局を Move16 で表してはならず（MUST NOT）、棋譜の木のイベントとして表さなければならない（MUST）。

`0x0000` を書いてよいのは、`RNOD` の根とイベントのノードの指し手欄だけである。書き手は、`EDGE`・`EDGC`・`MVLS` と指し手のノードに `0x0000` を書いてはならず（MUST NOT）、読み手はそれらの欄の `0x0000` を破損として扱わなければならない（MUST）。

### 6.3 正準局面符号（CPE）

局面が次の3条件をすべて満たすとき、その局面を「通常局面」と呼ぶ。満たさない局面を「拡張局面」と呼ぶ。

1. 各駒種の枚数（盤上と両者の持駒の合計）が、標準一式の枚数以下である。
2. 先手・後手の玉は、それぞれ盤上に高々1枚である。
3. 下の手順で符号化したときの符号長が 256bit 以下である。

書き手は、通常局面を CPE で、拡張局面を正準 SFEN で格納しなければならない（MUST）。書き手は、拡張局面を CPE で表してはならない（MUST NOT）。

注記：駒落ちの局面と、攻方玉のない詰将棋は、通常は通常局面に当たる。

書き手は、次の符号をこの順に連結して CPE を生成しなければならない（MUST）。

1. 手番：1bit（0 = 先手、1 = 後手）。
2. 先手玉の升：7bit。盤上にないときは 127。
3. 後手玉の升：7bit。盤上にないときは 127。
4. 盤面：升 0 から 80 の順に、玉のいる升を除いて1升ずつ書く。空き升は `0`。駒は `1` ＋ 駒種符号 ＋ 先後1bit（0 = 先手）＋ 成り1bit（金にはない）。駒種符号は、歩 `0`、香 `100`、桂 `101`、銀 `110`、金 `1110`、角 `11110`、飛 `11111`。
5. 盤外の駒：駒種ごとに、標準一式の枚数から盤上の枚数を引いた数だけ、1枚ずつ所在を書く。駒種は飛→角→金→銀→桂→香→歩の順、同じ駒種の中は先手の持駒、後手の持駒、駒箱の順とする。所在の符号は、先手の持駒 `0`、後手の持駒 `10`、駒箱 `11`。
6. 埋め草：合計が 256bit に満たないときは、残りを 0 で埋める。

ビット列は先頭から順に、各バイトの最上位ビットから詰める。複数ビットの整数（玉の升）は最上位ビットから書き、可変長符号は表記の左の文字から書く。

読み手は、復号した局面が通常局面の3条件を満たさない CPE、および埋め草に 1 が含まれる CPE を、破損として扱わなければならない（MUST）。

注記：両玉が盤上で、玉以外の38枚がすべて盤上にあるとき、手番1 ＋ 玉14 ＋ 空き升41 ＋ 歩72 ＋ 香桂銀金96 ＋ 角飛32 = 256bit となる。駒が1枚盤外へ出るたびに符号長は1bit以上減る。条件1・2を満たす局面が 256bit を超えるのは、玉が盤上になく、ほかの駒のほとんどが盤上にある場合に限られる。

### 6.4 局面キー

局面キー K は、通常局面では CPE 32バイトに対する XXH3-64（seed = 0、64bit 出力）、拡張局面では正準 SFEN の UTF-8 バイト列に対する XXH3-64（seed = 0）とする。K は u64 として格納しなければならない（MUST）。

読み手は、局面の一致を K だけで判定してはならず（MUST NOT）、CPE（拡張局面では正準 SFEN）のバイト列の一致で判定しなければならない（MUST）。

注記：XXH3 の出力はバージョンやプラットフォームによらず一定とされているため、独自のハッシュは定義しない。1兆局面では、同じ K を持つ組が約2.7万組生じる見込みである。

### 6.5 正準 SFEN

正準 SFEN は、SFEN の盤面・手番・持駒の3項目を半角空白1個で区切ったもので、手数の項目を含まない。書き手は、正準 SFEN を次の形で書かなければならない（MUST）。

- 盤面の連続する空き升は1桁の数字にまとめる。成駒は駒の文字の前に `+` を付ける。
- 持駒は先手（大文字）、後手（小文字）の順、それぞれ飛→角→金→銀→桂→香→歩の順に書く。2枚以上なら枚数を駒の文字の前に10進で書き、1枚なら書かない。持駒がなければ `-` とする。

例：`lnsgkgsnl/1r5b1/ppppppppp/9/9/9/PPPPPPPPP/1B5R1/LNSGKGSNL b -`

### 6.7 指し手の合法性

この仕様で、局面 P における指し手 m が「合法」であるとは、次の3つをすべて満たすことをいう。合法性を要求する規則（7.17、7.24、11.4 など）は、この定義による。

1. **構造の妥当性**：m が 6.2 の Move16 の条件を満たす。
2. **局面に対する妥当性**：動かす駒が P で手番側の駒として移動元にある（駒打ちでは手番側の持駒にある）。移動先に手番側の駒も相手の玉もない（駒打ちでは移動先が空き升）。駒の動きの規則に従い、飛び駒は途中の駒を越えない。成りは、成れる駒が移動元または移動先で敵陣（相手側の3段）に関わるときに限る。行き所のない駒を生じない。二歩にならない。
3. **対局規則**：手番側の玉が盤上にあるとき、指した後にその玉が相手の駒の利きにない（王手の放置と自殺手の禁止）。歩を打って相手の玉を詰ます手（打ち歩詰め）でない。

- 盤上にない玉に関する条件は適用しない。たとえば攻方の玉がない詰将棋の局面では、攻方の指し手に自玉への王手の判定を行わない。相手の玉が盤上にないとき、打ち歩詰めは生じない。
- 千日手・連続王手の千日手・持将棋など、手順の履歴や宣言に依存する規則は、指し手の合法性に含めない。
- 拡張局面にも同じ規則を適用する。
- 相手の玉を取る手は、どの局面でも合法でない。注記：玉を取ると玉が持駒に入り、その局面は正準 SFEN でも CPE でも表せない。

## 7. バイナリコンテナ（.spg）

.spg は、ヘッダ、セクション群、目録、末尾の複製からなる。最大1兆（10¹²）局面を想定する。

注記：エンジンは `KBKT` で範囲を絞り、`PKEY` を探索して `POSN` とエッジを引く。セクションを64バイト境界に置くのは、ファイル全体を mmap したまま読めるようにするためである。

### 7.1 配置

書き手は、次の配置に従わなければならない（MUST）。

1. ファイルは64バイトのヘッダで始まる。
2. 各セクションは、ファイル先頭から64の倍数のオフセットに置く。セクションどうしは重ならない。
3. 目録は、すべてのセクションの後の64の倍数のオフセットに置く。目録の複製は、目録の直後に置く。ヘッダの複製は、その後の64の倍数のオフセットに置き、ファイルの最後の64バイトとする。
4. ヘッダ、セクション、目録、複製のいずれにも属さないバイト（埋め草）は 0 とする。

### 7.2 整数の幅

添字・オフセット・件数・文字列参照は、次の例外を除き u64 で表す。

| 例外 | 幅 |
| --- | --- |
| 1局面のエッジ数 | u16 |
| `ENGN` 添字 | u16 |
| `AKEY` 添字 | u32 |
| 1棋譜のノード数・メタ情報の件数、`RNOD` の親までの距離 | u32 |
| シャード番号 | u32 |

注記：例外はいずれも値の上限が小さい欄である（合法手は最大593、1棋譜のノード数は実用上 2³² 未満）。

### 7.3 添字の範囲と寿命

- 局面の添字は「大域添字」とする。ファイル群全体の局面を `PKEY` の規定の順に並べたときの、0から始まる位置である。シャードはその連続区間なので、大域添字は「シャードの先頭局面の大域添字 ＋ シャード内の位置」に等しい。
- それ以外の添字は、そのファイル内の位置である。書き手は、エッジ・注釈・解析結果を、その対象と同じファイルに置かなければならない（MUST）。
- 大域添字は、同じビルド ID を持つファイル群の中でだけ有効である。局面の集合が変われば、シャードの構成が同じでも大域添字は変わる。局面の集合を変えるビルドを行う書き手は、新しいビルド ID を付け、大域添字を含むすべての参照（子局面、棋譜の開始局面、注釈と解析結果の対象、出現索引）を新しい添字で作り直さなければならない（MUST）。
- 棋譜は開始局面を CPE でも保持する（`RECS`）。注記：これにより、棋譜は局面グラフを再ビルドした後も、開始局面を検索し直すだけで新しい世代に付け替えられる。

### 7.4 ファイル種別と必須セクション

ファイル種別はヘッダのフラグで示す。書き手は各種別の必須セクションを含めなければならず（MUST）、読み手は必須セクションを欠くファイルを拒否しなければならない（MUST）。必須セクションは0件でもよい（MAY）。

| 種別 | 値 | 常に必須のセクション | 用途 |
| --- | --- | --- | --- |
| 単一 | 0 | `KBKT`、`PKEY`、`POSN`、`EDGE` と `EDGC` のどちらか一方、`CSUM` | 1ファイルで完結する定跡・棋譜集 |
| 局面シャード | 1 | 単一と同じ | マニフェストに属する局面系ファイル |
| 棋譜専用 | 2 | `RECS`、`RNOD`、`CSUM` | 棋譜系のセクションだけを置くファイル |

値3は予約である。書き手は、1つのファイルに `EDGE` と `EDGC` の両方を含めてはならない（MUST NOT）。さらに、次の条件付きの必須を満たさなければならない（MUST）。

- 文字列参照を1つでも含むファイルは `STRS` を含む。
- 評価値を持つエッジ（`EDGE` と `EDGC`）または `ANLS` を含むファイルは `ENGN` を含む。
- `ANNO` を含むファイルは `AKEY` を含む。
- 指し手列（`ANNO` の指し手列の値、`ANLS` の読み筋）を含むファイルは `MVLS` を含む。
- メタ情報を持つ棋譜を含むファイルは `META` を含み、原本を参照する棋譜を含むファイルは `RAWS` を含む。
- 注釈 `rights` を含むファイルは `RGHT` を含む。
- PROV を含むファイル、または対象の種類9（出典）の注釈を含むファイルは SRCS を含む。

v1.0 の書き手は、目録の bit0（必須）を、そのファイル種別で常に必須のセクション（上の表）にだけ立てなければならない（MUST）。

### 7.8 セクションの前置部（64バイト）

すべてのセクション（私用のセクションと将来のセクションを含む）は、次の64バイトの前置部で始まらなければならない（MUST）。レコードや本体は、セクション先頭から64バイトの位置から始まる。セクション内のオフセット（文字列参照、`RAWS` の位置など）は、前置部を含めたセクション先頭から数える。要素の添字（`MVLS` の先頭位置など）は、前置部の後の最初の要素を 0 とする。

### 7.9 予約領域

### 7.10 STRS（文字列プール）

### 7.15 KBKT（バケット表）と局面の検索

前置部の固有欄の先頭に b（u8）、その次に s（u8）を置く（7.8）。前置部の後に 2ᵇ ＋ 1 個の u64 を置く。

- b と s は 1 ≤ b ≤ 32、0 ≤ s ≤ 16、s ＋ b ≤ 64 を満たさなければならない（MUST）。s は、単一ファイルでは 0、局面シャードではマニフェストの s と同じ値でなければならない（MUST）。
- 局面キー K のバケット番号を `i(K) = ((K << s) mod 2⁶⁴) >> (64 − b)` とする。j 番目の要素は、このファイルの局面のうち i(K) < j を満たすものの数である。したがって最後の要素は、このファイルの局面数に等しい。
- v1.0 の書き手は、b = 16 としなければならない（MUST）。読み手は、上の範囲内のどの b・s も受け付けなければならない（MUST）。注記：b と s の欄は、将来の版で値を変えられるように残している。

読み手は、次の手順で局面を探さなければならない（MUST）。ただし手順4の探索方法は二分探索でも補間探索でもよい（MAY）。

1. 局面の K を計算する。
2. シャード分割されていれば、K の上位 s ビットが示すシャードを開く。
3. `KBKT` の i(K) 番目と i(K) ＋ 1 番目の要素を、探索範囲の下端と上端とする。
4. 範囲内で K と等しいキーの区間を求める。
5. 区間内の各局面の CPE（拡張局面では正準 SFEN）を比べ、一致する局面を答えとする。

注記：b = 16 の KBKT は1ファイルあたり約512 KiB である。1兆局面を s = 8 で分割すると、全シャードの合計で`KBKT` は128 MiB でメモリに常駐できる。1バケットは約6.0万キーである。

### 7.16 PKEY と POSN（局面表, 48バイト）

`PKEY` の i 番目は、`POSN` の i 番目の局面の K である。書き手は、局面を K の昇順に並べ、同じ K の中では通常局面を CPE のバイト列の辞書順に、その後に拡張局面を正準 SFEN の UTF-8 バイト列の辞書順に並べなければならない（MUST）。書き手は、同じ局面をファイル群の中に2回以上含めてはならない（MUST NOT）。

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 32 | CPE。拡張局面では先頭8バイトが正準 SFEN の `STRS` 参照で、残りは 0 |
| 32 | 8 | この局面のエッジの先頭位置（エッジ表のファイル内添字） |
| 40 | 2 | エッジ数 |
| 42 | 2 | フラグ。bit0 = 拡張局面、bit1 = 注釈あり、bit2 = 解析結果あり。ほかは予約 |
| 44 | 4 | 予約 |

書き手は、各局面のエッジを `POSN` の順に隙間なく連続して並べなければならない（MUST）。すなわち、最初の局面のエッジの先頭位置は 0 で、各局面のエッジの先頭位置は直前の局面の先頭位置とエッジ数の和に等しい。エッジ数は 593 以下でなければならない（MUST）。

| 0 | 2 | 指し手（Move16） |
| 2 | 2 | フラグ。bit0 = 選択しない（ネガティブ定跡）、bit1 = 評価値あり、bit2 = 勝敗統計あり、bit3 = 注釈あり、bit4 = 重みあり、bit5 = 解析結果あり。ほかは予約 |
| 4 | 2 | 探索深さ（`0xFFFF` = なし） |
| 6 | 2 | 評価したエンジンの `ENGN` 添字（`0xFFFF` = なし） |
| 8 | 4 | 選択重み（u32） |
| 12 | 4 | 評価値（EVAL、指した側の視点） |
| 16 | 8 | 指した後の局面の大域添字（全ビット 1 = ファイル群にない） |
| 24 | 8 | 出現数 |
| 32 | 8 | 指した側の勝ち数 |
| 40 | 8 | 引き分け数 |

書き手は、欄の値を次のとおりフラグと一致させなければならない（MUST）。

- bit1 が 0 なら、評価値は `0x80000000`、エンジン添字と探索深さは `0xFFFF`。bit1 が 1 なら、評価値は `0x80000000` 以外の正当な EVAL で、エンジン添字は有効な `ENGN` 添字。
- bit4 が 0 なら、選択重みは 0。bit4 が 1 なら、0 を含む任意の値。
- bit2 が 0 なら、出現数・勝ち数・引き分け数は 0。bit2 が 1 なら、勝ち数 ＋ 引き分け数 ≤ 出現数。負け数は、出現数 − 勝ち数 − 引き分け数である。
- 子局面の添字は、親局面に指し手を適用した局面がファイル群の局面表にあればその大域添字、なければ全ビット 1 である。
- 指し手は、親局面で合法（6.7）な手である。読み手は全件の合法性検査を省いてもよい（MAY）が、エンジンは指す直前に確認する（11.4）。
- bit1 が 1 のときも、探索深さは 0xFFFF（不明）でよい（MAY）。評価値がなく、探索深さなどだけが分かっている手は、bit1 を 0 とし、深さなどをそのエッジを対象とする ANLS（文脈 = 定跡生成、評価値なし）に格納しなければならない（MUST）。

書き手は、1つの局面のエッジを次の順に並べなければならない（MUST）。1つの局面のエッジの指し手は互いに異ならなければならない（MUST）。

1. bit4 が 1 のエッジを、選択重みの降順に。
2. その後に、bit4 が 0 のエッジを。
3. 1 の中で重みが等しいエッジどうし、および 2 のエッジどうしは、Move16 の昇順に。

注記：重みの決め方は書き手の方針であり、この仕様は定めない。重みの根拠を残したいときは、同じエッジに `ANLS`（文脈 = 定跡生成）を付けられる。

### 7.18 EDGC（指し手エッジ表・簡易形, 16バイト）

前置部の固有欄の先頭に、全エッジ共通の評価エンジン（`ENGN` 添字 u16）を置く（7.8）。bit1 が 1 のエントリが1件でもあれば、エンジン添字は有効でなければならず（MUST）、そうでなければ `0xFFFF`（なし）でなければならない（MUST）。各エントリは次のとおりである。

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 2 | 指し手（Move16） |
| 2 | 2 | フラグ（`EDGE` と同じ定義。bit2 と bit4 は 0） |
| 4 | 4 | 評価値（EVAL、指した側の視点） |
| 8 | 8 | 指した後の局面の大域添字（全ビット 1 = ファイル群にない） |

書き手は、bit1 が 0 のエッジの評価値を `0x80000000` にしなければならない（MUST）。書き手は、1つの局面のエッジを、bit1 が 1 のものを EVAL の整数値の降順に、その後に bit1 が 0 のものを並べ、同順位は Move16 の昇順に並べなければならない（MUST）。深さなど `EDGC` にない情報は、エッジに `ANLS` を付けて表す。

子局面の添字の規則は、`EDGE` と同じとする（MUST）。

`EDGE` を `EDGC` に変換する書き手は、`EDGC` に入らない情報（選択重み、勝敗統計、探索深さ、共通エンジンと異なるエンジンの評価値）を、可能なものは `ANLS` に移さなければならない（MUST）。移せない情報（選択重み、勝敗統計）を含む変換を、書き手は無損失として扱ってはならず（MUST NOT）、失った情報の件数と種類をファイル全体の注釈 `src.partial` に記録しなければならない（MUST）。

書き手は、利用者の指定がない限り、失う情報がないとき（選択重み・勝敗統計・探索深さがなく、評価したエンジンが1つだけのとき）に限って `EDGC` を選ぶべきである（SHOULD）。

### 7.19 ANNO（注釈表, 24バイト）

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 1 | 対象の種類。1 = 局面、2 = エッジ、3 = 棋譜ノード、4 = 棋譜、5 = ファイル全体、6 = エンジン、7 = 注釈エントリ、8 = 解析結果エントリ、9 = 出典。ほかは予約 |
| 1 | 1 | 値の型（下表） |
| 2 | 2 | 予約 |
| 4 | 4 | キー（`AKEY` 添字） |
| 8 | 8 | 対象の添字。局面は大域添字、ファイル全体は 0、注釈エントリは `ANNO` の添字、解析結果エントリは `ANLS` の添字、出典は `SRCS` の添字、それ以外はファイル内添字 |
| 16 | 8 | 値 |

| 型 | 名前 | 値欄の符号化 |
| --- | --- | --- |
| 1 | 整数 | i64 |
| 2 | 実数 | IEEE 754 binary64 |
| 3 | 文字列 | `STRS` 参照 |
| 4 | 指し手列 | 下位48bit が `MVLS` の先頭位置、上位16bit が手数 |
| 5 | 真偽 | 0 = 偽、1 = 真 |

- 型6〜255 は予約である。v1.0 の書き手は予約の型を書いてはならない（MUST NOT）。読み手は、未知の型の注釈を無視しなければならず（MUST）、ファイルを書き直す書き手はそれを保持しなければならない（MUST）。
- 真偽型の値が 0 と 1 以外のとき、読み手は破損として扱わなければならない（MUST）。
- 書き手は、注釈を対象の種類の昇順、同じ種類の中では対象の添字の昇順に並べ、同じ対象の注釈は記録順を保たなければならない（MUST）。読み手は、同じ対象・同じキーの注釈が複数あるとき、この順で復元しなければならない（MUST）。
- 書き手は、局面・エッジ・棋譜ノード・棋譜のフラグの「注釈あり」を、その対象の注釈が存在するときに限り立てなければならない（MUST）。
- 実数型の値は有限でなければならない（MUST）。読み手は、NaN と無限大を破損として扱わなければならない（MUST）。
- 対象の種類7（注釈エントリ）の注釈は、キーが rights でなければならず（MUST）、対象の種類7の注釈を対象にしてはならない（MUST NOT）。対象の種類8（解析結果エントリ）の注釈は、キーが rights であるか、src. または x. で始まるものでなければならない（MUST）。
- 注釈は対象の種類の昇順に並ぶので、対象の種類7の注釈は、自分より後ろの添字の注釈（対象の種類8・9の注釈）を指すことがある。読み手は、対象の種類7の注釈を、ANNO の前後どちらの添字を指していても対応づけなければならない（MUST）。

### 7.20 ANLS（解析結果表, 56バイト）

1件のエントリが、1回の思考・解析の結果を表す。

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 1 | 対象の種類。1 = 局面、2 = エッジ、3 = 棋譜ノード |
| 1 | 1 | 文脈。0 = 対局中の思考、1 = 検討・解析、2 = 定跡生成。ほかは予約 |
| 2 | 2 | 候補順位（MultiPV、1 始まり。0 = なし） |
| 4 | 2 | エンジン（`ENGN` 添字） |
| 6 | 1 | 評価値の境界。0 = 確定値、1 = 下限、2 = 上限。ほかは予約 |
| 7 | 1 | フラグ。bit0 = 深さあり、bit1 = 選択深さあり、bit2 = ノード数あり、bit3 = 時間あり、bit4 = 読み筋あり、bit5 = 勝率あり、bit6 = 視点未確定。bit7 は予約 |
| 8 | 8 | 対象の添字（局面は大域添字、それ以外はファイル内添字） |
| 16 | 4 | 評価値（EVAL。なしは `0x80000000`） |
| 20 | 2 | 深さ |
| 22 | 2 | 選択深さ |
| 24 | 8 | ノード数 |
| 32 | 4 | 思考時間（ミリ秒） |
| 36 | 2 | 勝率（万分率、8.1） |
| 38 | 2 | 予約 |
| 40 | 8 | 読み筋（下位48bit が `MVLS` の先頭位置、上位16bit が手数） |
| 48 | 8 | 探索の識別子（0 = 単独の結果） |

- エンジン添字は有効でなければならない（MUST）。
- 書き手は、フラグの立っていない欄に 0 を書かなければならない（MUST）。
- 並び順と「解析結果あり」フラグの規則は、`ANNO` と同じとする（MUST）。
- 書き手は、1回の探索（USI の `go` 1回など）で得た複数の結果（MultiPV の各候補、途中経過）に、同じ 0 でない探索の識別子を付けなければならない（MUST）。同じ探索の識別子を持つ結果は、同じ対象・同じエンジンでなければならない（MUST）。識別子の値はファイル内で区別できればよく、ほかの意味を持たない。
- bit6（視点未確定）が立った結果では、評価値と勝率は元データの値をそのまま格納する。読み手は、視点未確定の評価値と勝率を、手の選択や大小比較に使ってはならない（MUST NOT）。
- 解析結果は、思考・解析した局面を対象とする。棋譜ノードを対象とするとき、対局中の思考（文脈 0）は、その思考の結果として指された手のノードの親（思考した局面のノード）に付け、検討・解析（文脈 1）は解析した局面のノードに付けなければならない（MUST）。読み筋は、対象の局面から始まる。取り込み器は、指し手の後に書かれた思考コメント（KIF のコメントなど）を、この規則で付け替えなければならない（MUST）。

### 7.21 MVLS（指し手列プール, 2バイト）

`MVLS` は Move16 の配列である。各要素は Move16 の条件を満たさなければならない（MUST）。指し手列は、先頭位置（要素の添字）と手数で参照する（`ANNO` の指し手列の値、`ANLS` の読み筋）。読み筋は、対象の局面（エッジでは指した後の局面）から合法な手順であるべきである（SHOULD）。

### 7.22 PROV（由来情報表, 64バイト）

各エントリは、1つの出典が1つの局面またはエッジに寄与した内容を表す。統合後の局面・エッジの欄とは別に、出典ごとの値を保つ。

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 1 | 対象の種類。1 = 局面、2 = エッジ。ほかは予約 |
| 1 | 1 | 予約 |
| 2 | 2 | フラグ（`EDGE` と同じ定義）。bit0 = 選択しない、bit1 = 評価値あり、bit2 = 勝敗統計あり、bit4 = 重みあり。ほかは予約 |
| 4 | 2 | 探索深さ（`0xFFFF` = なし） |
| 6 | 2 | 評価したエンジンの `ENGN` 添字（`0xFFFF` = なし） |
| 8 | 4 | 選択重み（u32） |
| 12 | 4 | 評価値（EVAL、指した側の視点） |
| 16 | 8 | 対象の添字（局面は大域添字、エッジはファイル内添字） |
| 24 | 8 | 出現数 |
| 32 | 8 | 指した側の勝ち数 |
| 40 | 8 | 引き分け数 |
| 48 | 4 | 出典（`SRCS` 添字） |
| 52 | 12 | 予約 |

- オフセット 2〜15 と 24〜47 の配置と意味は `EDGE` と同じであり、欄とフラグの対応も `EDGE` の規則に従わなければならない（MUST）。対象が局面のエントリでは、フラグと各欄を「値なし」にする。すなわち、フラグ・選択重み・出現数・勝ち数・引き分け数は 0、評価値は `0x80000000`、探索深さとエンジン添字は `0xFFFF` とする（MUST）。
- 書き手は、エントリを対象の種類、対象の添字、出典の添字の昇順に並べなければならず（MUST）、同じ対象と出典の組を2件以上書いてはならない（MUST NOT）。
- 書き手は、`PROV` を、それが参照するエッジと同じファイルに置かなければならない（MUST）。

注記：`EDGE` と同じ位置に同じ欄を置いているので、`EDGE` の読み書きの処理をそのまま使える。

注記：出典が1つだけのファイル群には `PROV` は不要である。出典が複数のとき、容量は「寄与した出典の数 × 64 B」だけ増える。

### 7.23 RECS（棋譜表, 80バイト）

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 32 | 開始局面の CPE。拡張局面では先頭8バイトが正準 SFEN の `STRS` 参照で、残りは 0 |
| 32 | 8 | 開始局面の大域添字。同じビルドの局面表にあればその添字、なければ全ビット 1（MUST） |
| 40 | 8 | 先頭ノードの `RNOD` 添字 |
| 48 | 8 | 先頭メタ情報の `META` 添字（件数が 0 なら 0） |
| 56 | 8 | 取り込み元の `RAWS` 添字（全ビット 1 = なし） |
| 64 | 4 | ノード数（1 以上） |
| 68 | 4 | メタ情報の件数 |
| 72 | 4 | 開始手数（SFEN の第4項目に相当。不明なら 0） |
| 76 | 1 | 結果。0 = 不明、1 = 先手勝ち、2 = 後手勝ち、3 = 引き分け。ほかは予約 |
| 77 | 1 | フラグ。bit0 = 開始局面が拡張局面、bit1 = 対局の記録ではない（研究手順・作成した手順など）、bit2 = 注釈あり。ほかは予約 |
| 78 | 2 | 予約 |

「先手」は SFEN の大文字側をいう（駒落ちでは下手）。結果は終局イベントとは独立に記録する。勝敗の決め方は 10.2 で定める。

### 7.24 RNOD（棋譜ノード表, 16バイト）

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 4 | 親までの距離（自分の添字 − 親の添字。根は 0） |
| 4 | 2 | 指し手（Move16。根とイベントでは `0x0000`） |
| 6 | 1 | 種類。0 = 根、1 = 指し手、2 = イベント |
| 7 | 1 | イベントコード（イベント以外では 0） |
| 8 | 4 | 消費時間（ミリ秒、全ビット 1 = なし） |
| 12 | 2 | フラグ。bit0 = 注釈あり、bit1 = 解析結果あり。ほかは予約 |
| 14 | 2 | 予約 |

ノードの種類ごとに、各欄は次の値でなければならない（MUST）。読み手は、これに反するノードを破損として扱わなければならない（MUST）。

| 種類 | 親までの距離 | 指し手 | イベントコード | 子 |
| --- | --- | --- | --- | --- |
| 0 = 根 | 0 | `0x0000` | 0 | 持てる |
| 1 = 指し手 | 1 以上 | `0x0000` 以外 | 0 | 持てる |
| 2 = イベント | 1 以上 | `0x0000` | 定義済みのコード | 持てない |

書き手は、1つの棋譜のノードを次の規則で並べなければならない（MUST）。

1. 前順（親が子より先）に並べる。最初のノードが根で、根はちょうど1つである。
2. 根以外のノードの親までの距離は、1 以上で、その棋譜の中での自身の位置以下である。
3. 同じ親の子は記録順に並べる。最初の子が本譜、2番目以降が変化である。
4. イベントのノードは子を持たない。
5. 指し手のノードの指し手は、親のノードの局面で合法（6.7）である。

注記：親は前順で必ず前にあるので、親への参照は棋譜内の相対距離で足りる。ノード全体の数が1兆を超えても、1手あたり16バイトのままである。

### 7.25 META と OCCR

- `META` の各エントリ（16バイト）は、キーと値の `STRS` 参照の組である。書き手は、取り込み元の順序を保たなければならない（MUST）。
- `OCCR` の各エントリ（24バイト）は、局面の大域添字・棋譜の添字・ノードの添字（各 u64）の組である。`OCCR` は、参照する棋譜（`RECS`）と同じファイルに置かなければならず（MUST）、棋譜とノードの添字はそのファイル内の添字である。`OCCR` は、局面表に含まれる局面に到達するすべてのノード（変化を含む）を列挙し、局面・棋譜・ノードの添字の昇順に並べなければならない（MUST）。

### 7.26 棋譜からの勝敗統計の集計

書き手が棋譜から `EDGE` の勝敗統計を作るときは、次の規則に従わなければならない（MUST）。

1. 集計の対象は、結果が不明でなく、`RECS` のフラグ bit1 が 0 の棋譜の本譜だけとする。変化は対象に含めない。
2. 局面の一致は CPE（拡張局面では正準 SFEN）で判定し、手数は問わない。
3. ある局面のある指し手のエッジについて、出現数は「本譜でその局面からその指し手を指した対象棋譜の数」、勝ち数は「そのうち指した側が勝った棋譜の数」、引き分け数は「そのうち引き分けの棋譜の数」とする。
4. 1つの棋譜の本譜で、同じ局面から同じ指し手が複数回指されても、その棋譜につき1回と数える。

書き手が上と異なる規則で集計した統計を書くときは、ファイル全体の注釈 `stat.rule`（文字列）にその規則を書かなければならない（MUST）。

### 7.27 RAWS（原本表）

前置部の件数は原本の数、レコード長は 48 である（7.8）。前置部の後に1件48バイトの目次を件数分置き、その後に原本のバイト列を置く。

| オフセット | サイズ | 内容 |
| --- | --- | --- |
| 0 | 8 | 原本のバイト列の位置（セクション先頭から） |
| 8 | 8 | 格納された長さ |
| 16 | 8 | 元の長さ（圧縮前） |
| 24 | 8 | 形式名（`STRS` 参照。例：`kif`、`csa`、`yaneuraou-db2016`） |
| 32 | 8 | 元のファイル名（`STRS` 参照。全ビット 1 = なし） |
| 40 | 1 | 圧縮方式。0 = なし、1 = zstd。ほかは予約 |
| 41 | 7 | 予約 |

圧縮方式が 1 のとき、格納されたバイト列は1つの zstd フレームでなければならない（MUST）。

### 7.28 シャードとマニフェスト（.spgm）

大きなファイル群は、K の上位 s ビット（0 ≤ s ≤ 16）で 2ˢ 個の局面シャードに分け、マニフェストで束ねる。シャード番号 i の局面シャードは、K の上位 s ビットが i に等しい局面をすべて含まなければならない（MUST）。v1.0 の書き手は、局面シャードに分割するときは s = 8（256 シャード）とし、分割しないときは s = 0 としなければならない（MUST）。s = 0 のとき、局面シャードは1つで、シャード番号は 0 である。

書き手は、ファイル名を次の形にしなければならない（MUST）。`<名前>` は英数字・`-`・`_` からなり、16進数は英小文字で書く。

- 局面シャード：`<名前>.<ビルドIDを16進16桁>.<シャード番号を16進4桁>.spg`
- 棋譜専用ファイル：`<名前>.<ビルドIDを16進16桁>.rec.spg`
- マニフェスト：`<名前>.spgm` と `<名前>.spgm.bak`

マニフェストの配置は次のとおりとする。

| オフセット | サイズ | 内容 |
| --- | --- | --- |

| 続き | 100 | 署名（フラグ bit0 のときだけ）。11.8 で定める |

キーの下限と上限は、そのシャードが担当する範囲であり、実際に格納した局面のキーの最小・最大ではない。書き手は、局面数が 0 のシャードにも同じ式の値を書かなければならない（MUST）。

注記：K の上位 s ビットを `K >> (64 − s)` で求める実装は、s = 0 のとき64ビットのシフトになり、多くの言語で未定義動作または例外になる。s = 0 を別に扱うこと。7.15 の i(K) も同様である。

### 7.29 配布時の圧縮

.spg そのものは mmap で読むために圧縮しない。配布や保管のために圧縮するときの規則を次に定める。圧縮の形式・手法・拡張子は規定しない。

- 書き手は、ファイル群の各ファイルを任意の形式・手法で圧縮してよい（MAY）。圧縮の単位（ファイルごと、複数ファイルのまとめなど）、パラメータ、圧縮後のファイル名と拡張子も、書き手が選んでよい（MAY）。圧縮したファイルと圧縮していないファイルを混ぜて配布してもよい（MAY）。
- 展開したファイルは、元のファイルと同じバイト列でなければならず（MUST）、ファイルとして置くときは 7.28 のファイル名を持たなければならない（MUST）。
- マニフェストに書くファイル長とハッシュは、圧縮前の値とする（MUST）。マニフェスト（`.spgm` と `.spgm.bak`）はファイル群を検証する起点なので、圧縮せずに配布すべきである（SHOULD）。
- 読み手は、元のファイルと同じバイト列を得てから使わなければならない（MUST）。展開の方法（ファイルへの書き出し、メモリ上の展開、必要な範囲だけの展開）は、読み手が選んでよい（MAY）。
- 読み手は、展開したデータに 11章の検証を行わなければならない（MUST）。圧縮形式が独自の検査値を持ち、それが一致しないときは、展開の失敗として拒否しなければならない（MUST）。
- この仕様は、読み手に特定の圧縮形式への対応を求めない。読み手は、展開できない形式のファイルを拒否してよい（MAY）。

注記：圧縮は配布と保管のためだけのものである。展開後のバイト列が元と同じであれば、どう圧縮したかはファイル群の意味に影響しない。zstd、xz、tar との組み合わせなどを使える。大きなシャードには、一部だけを展開できる形式（zstd の seekable 形式など）が向く。

## 8. 注釈スキーマ

この章は、評価値の表現、注釈のキー、権利情報の適用、由来情報と統合、終局イベント、範囲外の値の扱いを定める。

### 8.1 評価値（EVAL, i32）

| 値 | 意味 |
| --- | --- |
| `0x80000000`（INT32\_MIN） | なし |
| 単位ごとの通常値の値域（下表）内の値 | 通常の評価値 |
| +(2³⁰ − n)、1 ≤ n ≤ 65535 | 視点側が n 手（片側の手番を1手と数える）で詰ます |
| −(2³⁰ − n)、1 ≤ n ≤ 65535 | 視点側が n 手で詰まされる |
| ±2³⁰ | 詰ます・詰まされるが手数は不明 |

通常値の値域と意味は、評価したエンジンの単位（`ENGN`）で決まる。

| 単位 | 通常値の意味 | 通常値の値域 | 反対側の視点への変換 |
| --- | --- | --- | --- |
| 1 = 歩基準の点数 | 符号付きの点数 | −(2²⁴ − 1) 〜 +(2²⁴ − 1) | 符号を反転 |
| 2 = 勝率 | 期待得点（勝ち = 1、引き分け = 0.5、負け = 0）の万分率 | 0 〜 10000 | 10000 から引く |
| 3 = エンジン固有の生の値 | 符号付きで、反対側の値が符号の反転になる値 | −(2²⁴ − 1) 〜 +(2²⁴ − 1) | 符号を反転 |

詰みの値は、どの単位でも符号の反転で反対側の視点に変換する。

- 書き手は、上の表のどれにも当たらない値を EVAL として書いてはならない（MUST NOT）。読み手は、そのような値を破損として扱わなければならない（MUST）。
- 視点は固定である。エッジの評価値（`ANLS` の対象がエッジの場合を含む）は、その手を指した側から見た値とする。局面と棋譜ノードの評価値（`ANLS` の対象が局面・棋譜ノードの場合を含む）は、その局面で手番の側から見た値とする。取り込み器は、ほかの視点で書かれた元データを、上の表の規則で変換しなければならない（MUST）。元データの視点を確定できないとき、取り込み器は値を変換してはならず（MUST NOT）、元の値をそのまま ANLS に格納して視点未確定のフラグを立てなければならない（MUST）。元の値が EVAL の値域に収まらないときは、評価値を 0x80000000（なし）とし、元の値を文字列のまま、その解析結果エントリを対象とする注釈 src.<形式>.raw\_eval に記録しなければならない（MUST）。書き手は、エッジの評価値の欄には視点の確定した値だけを書かなければならない（MUST）。
- `ANLS` の勝率欄は、単位2と同じ意味・値域・変換規則に従う。書き手は 10000 を超える値を書いてはならない（MUST NOT）。
- 読み手は、単位の異なる評価値を換算せずに大小比較してはならない（MUST NOT）。

注記：正当な値を32bit空間のごく一部に限っているのは、ビット反転を値域外として検出しやすくするためである。たとえば bit 24〜29 の反転は、単位1の通常値をどの正当な値にも写さない。

### 8.2 注釈のキー

書き手は、評価値・深さ・ノード数・読み筋などの解析情報を `ANNO` に格納してはならず（MUST NOT）、`ANLS` に格納しなければならない（MUST）。注記：独立した注釈にすると、同じ対象に複数の解析があるとき、どの値が組なのかを復元できない。

標準キーは次のとおりである。書き手は、標準キーを表の型と対象でだけ使わなければならない（MUST）。

| キー | 型 | 対象 | 内容 |
| --- | --- | --- | --- |
| `comment` | 文字列 | 局面・エッジ・棋譜ノード・棋譜・ファイル全体・エンジン・出典 | 人間のコメント。同じ対象に複数可 |
| `bookmark` | 文字列 | 棋譜ノード | しおり（KIF の「基本図」など） |
| `event.raw` | 文字列 | イベントノード | 対応表にない終局表記の原文 |
| `rights` | 整数（i64） | 局面・エッジ・棋譜ノード・棋譜・ファイル全体・注釈エントリ・解析結果エントリ・出典 | 権利情報。値は 0 以上の有効な `RGHT` の添字。同じ対象に複数可（8.3） |
| `src.engine` | 文字列 | エンジン | 「不明」エンジンの取り込み元 |
| `src.partial` | 文字列 | ファイル全体 | 部分取り込みで欠けたエントリの件数と種類 |
| `stat.rule` | 文字列 | ファイル全体 | 標準と異なる勝敗統計の集計規則 |
| `merge.rule` | 文字列 | ファイル全体 | 出典を統合したときに重みと評価値を合成した規則（8.4） |
| `src.<形式>.<名前>` | 任意 | すべて | 取り込み元の表記や原値を復元するための情報（10章） |
| `src.range.<属性名>` | 文字列 | エッジ・解析結果エントリ・棋譜ノード・棋譜・エンジン | 範囲外の値を丸めたときの元の値（8.6） |

- 標準キーで表せない情報には、`x.<提供元>.<名前>` の形のキーを使わなければならない（MUST）。
- 書き手は、上のどれにも当たらないキー（`x.` と `src.` で始まらない未定義のキー）を作ってはならない（MUST NOT）。
- 読み手は、知らないキーの注釈を無視しなければならない（MUST）。ファイルを書き直す書き手は、それを保持しなければならない（MUST）。

### 8.3 権利情報の適用

注釈 `rights`（整数）は、`RGHT` の添字で権利情報を参照する。局面・エッジ・棋譜ノード・棋譜・ファイル全体・注釈エントリ・解析結果エントリ・出典に付けられ、同じ対象に複数付けてもよい（MAY）。

あるデータの「有効な権利情報」は、そのデータ自身の `rights` 注釈が参照するエントリの集合とする。自身に `rights` 注釈がなければ、次の順に上位をたどって最初に見つかった集合とする。

- 注釈エントリ・解析結果エントリ → その対象（以降はその対象の規則に従う）
- 棋譜ノード → その棋譜 → ファイル全体
- エッジ → その局面 → ファイル全体
- 局面、棋譜、出典 → ファイル全体

規則は次のとおりである。

- 書き手は、権利情報の異なるデータを1つのファイル群にまとめるとき、統合しないデータ（棋譜、注釈、解析結果）の有効な権利情報が元と変わらないように `rights` 注釈を付けなければならない（MUST）。
- 統合した局面・エッジの有効な権利情報は、それに寄与したすべての出典の権利情報の和集合でなければならない（MUST）。出典ごとの対応は `PROV` で保つ（8.4）。
- 書き手は、利用者の明示的な指示がない限り、`RGHT` のエントリと `rights` 注釈を削除・変更してはならない（MUST NOT）。
- ファイル全体を対象とする `rights` 注釈と、それが参照するエントリの内容は、マニフェストで束ねるすべてのファイルで同じでなければならない（MUST）。
- データを利用者に表示する読み手（GUI など）は、表示しているデータの有効な権利情報を、利用者が確認できるようにすべきである（SHOULD）。

### 8.4 由来情報と統合

「出典」は、統合の入力となった1つのデータの集まりである。出典は `SRCS` に登録し、出典ごとの寄与を `PROV` に記録する。

- 2つ以上の出典の局面・エッジを1つのファイル群に統合する書き手は、各局面・各エッジについて、寄与したすべての出典の `PROV` エントリを書かなければならない（MUST）。ある出典が局面やエッジに「寄与した」とは、その出典のデータにその局面やエッジが含まれていたことをいう。
- 書き手は、利用者の明示的な指示がない限り、`PROV` を書かずに複数の出典を統合してはならない（MUST NOT）。指示に従って `PROV` なしで統合した書き手は、その旨を `merge.rule` に書かなければならない（MUST）。
- 出典ごとの勝敗統計を `PROV` に記録したエッジでは、`EDGE` の出現数・勝ち数・引き分け数は、`PROV` の各値の和でなければならない（MUST）。
- 統合後のエッジの重みと評価値をどう決めるかは書き手の方針による。`PROV` を含むファイル群を書く書き手は、その規則を `merge.rule` に書かなければならない（MUST）。
- 前項の「明示的な指示」は、PROV を書かないことを選ぶ利用者の指定（ツールの設定や引数など）をいう。統合を指示しただけでは、PROV を省く指示とみなさない。

注記：読み手は `PROV` を使って、特定の出典に由来する局面・エッジと、その出典での値だけを取り出せる。

### 8.5 終局イベント

イベントコードは、イベントノードの局面で手番の側から見た意味を表す。取り込み器は、先後で書かれた元データ（CSA の `%+ILLEGAL_ACTION` など）を、この意味に変換しなければならない（MUST）。

| コード | 意味 | テキスト表現の名前 | KIF の例 | CSA の例 |
| --- | --- | --- | --- | --- |
| 1 | 投了 | `resign` | 投了 | `%TORYO` |
| 2 | 中断 | `interrupt` | 中断 | `%CHUDAN` |
| 3 | 千日手 | `sennichite` | 千日手 | `%SENNICHITE` |
| 4 | 持将棋 | `jishogi` | 持将棋 | `%JISHOGI` |
| 5 | 時間切れ（手番側の負け） | `timeout` | 切れ負け | `%TIME_UP` |
| 6 | 反則（手番側の負け） | `illegal_loss` | 反則負け | `%ILLEGAL_MOVE`、手番に応じて `%±ILLEGAL_ACTION` |
| 7 | 反則（手番側の勝ち） | `illegal_win` | 反則勝ち | 手番に応じて `%±ILLEGAL_ACTION` |
| 8 | 入玉宣言勝ち（手番側の勝ち） | `declare_win` | 入玉勝ち | `%KACHI` |
| 9 | 詰み（手番側の負け） | `mate` | 詰み | — |
| 10 | 不詰 | `nomate` | 不詰 | — |
| 11 | 引き分け | `draw` | — | `%HIKIWAKE` |
| 12 | 最大手数 | `max_moves` | — | `%MAX_MOVES` |
| 13 | 待った（直前の手順の取り消し） | `matta` | 待った | `%MATTA` |
| 14 | 不戦（手番側の勝ち） | `default_win` | 不戦勝 | — |
| 15 | 不戦（手番側の負け） | `default_loss` | 不戦敗 | — |
| 255 | その他（原文を `event.raw` に記録） | `other` | — | — |

コード 0 と 16〜254 は予約である。表の KIF・CSA の表記は代表例である。取り込み器は、表にない表記を意味の同じコードに写し、該当するコードがなければコード 255 として原文を `event.raw` に記録しなければならない（MUST）。

不戦の棋譜は、根の直後に不戦のイベント（コード 14 または 15）だけを置く。コードは、開始局面の手番の側（平手なら先手）から見た意味で選ぶ。取り込み器は、元データが勝者・敗者の側で書いた不戦を、この意味に変換しなければならない（MUST）。

待ったは、次の形で表さなければならない（MUST）。

- 取り消された手順（1手以上）は、取り消された最初の手の親から分かれる変化とし、その末尾に待ったのイベント（コード 13）を置く。
- 待ったの後に実際に指された手順は、同じ親の子として、取り消された手順より前（本譜の側）に置く。

注記：取り消された手順は変化になるので、結果の決定（10.2）にも勝敗統計の集計（7.26）にも使われない。イベントは子を持たないという規則（7.24）もそのまま保たれる。

### 8.6 範囲外の値と丸め

取り込み元やエンジンの値が、書き込む欄の範囲（各節と付録E）を外れるとき、書き手はこの節に従わなければならない（MUST）。書き手は、範囲外の値を欄の幅に切り詰めたり（剰余）、符号を変えたりして書いてはならない（MUST NOT）。

元の値は、その欄を持つ対象を対象とする文字列型の注釈 `src.range.<属性名>` に、取り込み元の表記のまま記録する。`<属性名>` は 9.5 の属性名（`t`、`ms`、`depth`、`eval` など）とする。例：解析結果の思考時間が範囲外なら、その解析結果エントリを対象とする `src.range.ms`。

`PROV` の欄の元の値は、その `PROV` エントリが対象とするエッジを対象とし、キーを `src.range.prov.<属性名>`、値を「出典の添字」、`:`、元の値をこの順につないだ文字列として記録する（例：`3:70000`）。

| 場合 | 例 | 扱い |
| --- | --- | --- |
| 上限を超える | 思考時間・消費時間が約49.7日超、探索深さ・候補順位が 65,535 超、選択重みが 2³² − 1 超 | 欄の最大値（「なし」を表す値を除く）に丸め、元の値を記録する（MUST） |
| 「なし」を表す値と等しい | 消費時間がちょうど 4,294,967,295 ms、`EDGE` の探索深さが 65,535 | その1つ手前の値に丸め、元の値を記録する（MUST） |
| 下限を下回る | 負の時間・深さ・ノード数・勝敗統計、候補順位 0 以下、開始手数 0 以下 | 欄を「なし」（フラグを下ろすか、なし・不明を表す値）にし、元の値を記録する（MUST）。勝敗統計のように複数の欄が1つのフラグを共有するときは、その組をすべて「なし」にする |
| 評価値 | 通常値の値域外、勝率が 0 未満または 10000 超 | 視点が確定していれば、値域の端（±(2²⁴ − 1)、0、10000）に丸め、元の値を記録する（MUST）。詰み手数が 65,535 を超える詰みは ±2³⁰（手数不明）とし、元の手数を記録する（MUST）。視点が未確定の値は 8.1 による |
| 精度が細かすぎる | ミリ秒未満の時間、小数の評価値・勝率 | 時間はミリ秒未満を切り捨て、評価値と勝率は最も近い値に丸める（ちょうど中間なら 0 から遠い側）（MUST）。丸めで値が変わったときは、元の値を記録すべきである（SHOULD） |
| 構造の上限を超える | 1局面のエッジが 593 超、指し手列が 65,535 手超、棋譜のノード数が 2³² − 1 超、文字列が 2³² − 1 バイト超 | 丸められない。取り込み器は L1 を満たせない入力として扱う（10.2）。部分取り込みでは上限までを格納し（指し手列は先頭から）、残りの件数と種類を `src.partial` に記録する（MUST） |
| 注釈の値 | i64 を超える整数、非有限の実数 | 型がスキーマで決まらないキーでは、同じキーの文字列型の注釈として原文のまま記録する（MUST）。型が決まる標準キーでは、L1 を満たせない入力として扱う |

- 勝敗統計を丸めるときは、勝ち数 ＋ 引き分け数 ≤ 出現数を保たなければならない（MUST）。
- 読み手は、`src.range.<属性名>` の注釈を持つ欄の値を、丸めた値として扱わなければならない（MUST）。上限に丸めた値は「その値以上」、下限を下回って「なし」にした欄は「不明」を意味する。
- ファイルの中の値が欄の範囲を外れることはない。読み手は、範囲外の値（値域外の EVAL、10000 を超える勝率、593 を超えるエッジ数など）を破損として扱わなければならない（MUST）。

注記：上限に丸めるのは、「非常に長い」「非常に深い」という情報を欄の値として使えるようにするためである。元の値は注釈に残るので、取り込みは無損失のままである。

## 9. テキスト表現（.spgt）

.spgt は、SPG の論理データを行単位で書いたテキスト形式である。バイナリの全情報を再現する形式ではない（9.1 を参照）。差分確認・手編集・小さな棋譜のやり取りに使う。

注記：1兆局面規模のファイル全体を .spgt にすることは想定しない。

### 9.1 往復の範囲

.spg から .spgt へ、または .spgt から .spg へ変換する実装は、次のデータを過不足なく変換しなければならない（MUST）。

- エンジン表のすべてのエントリ。
- 局面表のすべての局面と、各局面のエッジの全欄。
- 棋譜表のすべての棋譜（開始局面、開始手数、結果、フラグ、メタ情報とその順序）と、すべてのノード。
- すべての注釈（ファイル全体・エンジン・出典・注釈エントリ・解析結果エントリを対象とするものを含む）と、同じ対象内の順序。
- すべての解析結果と、同じ対象内の順序。
- 権利情報表のすべてのエントリ。
- 出典表と由来情報表のすべてのエントリ。

次のデータは往復の範囲外とする。.spgt から .spg を作る書き手は、派生セクションを作り直し、新しいビルド ID を付けなければならない（MUST）。

- `RAWS`、未知のセクション、派生セクション（`KBKT`・`PKEY`・`OCCR`・`CSUM`・`BLK3`）。
- セクションの配置、文字列プールの並びと重複、ビルド ID。
- エッジを EDGE と EDGC のどちらで格納するか。.spgt から .spg を作る書き手が選ぶ。

.spg を .spgt に変換する実装は、予約の型（6〜255）の注釈を含むファイルを変換してはならず（MUST NOT）、エラーとして報告しなければならない（MUST）。

局面表に入るのは `pos` 行の局面だけである。棋譜の開始局面や途中の局面は、`pos` 行がなければ局面表に入らない。棋譜の開始局面の大域添字は、同じファイルに同じ局面の `pos` 行があればその局面を、なければ全ビット 1 を指す。

### 9.2 字句の規則

- 文字コードは BOM のない UTF-8 でなければならない（MUST）。書き手は改行に LF だけを使わなければならない（MUST）。読み手は CRLF を受け付けてもよい（MAY）。
- 1行目は `SPG-TEXT 1.0` でなければならない（MUST）。
- 2行目以降の空行と、`#` で始まる行（メモ）は、どの行の間に置いてもよい（MAY）。読み手はこれらを無視しなければならない（MUST）。メモは往復の範囲外である。
- 読み手は、各行を先頭から順に読み、次の3つの状態に従って字句に分けなければならない（MUST）。行の先頭は通常状態である。
  - 通常状態：半角空白は語の区切りである。`"` を読むと文字列状態に、`[` を読むと指し手列状態に入る。
  - 文字列状態：RFC 8259 の文字列の規則に従い、`\` で始まるエスケープを解釈する。エスケープされていない `"` を読むと通常状態に戻る。この状態では、半角空白・`=`・`[`・`]`・`#` は値の一部である。
  - 指し手列状態：半角空白は指し手の区切りである。`]` を読むと通常状態に戻る。この状態で `"` と `[` は現れてはならない（MUST NOT）。
- 語の区切りは、通常状態の半角空白だけである。書き手は区切りに半角空白1個を使わなければならず（MUST）、読み手は1個以上の半角空白を区切りとして受け付けなければならない（MUST）。
- 次のものは構文誤りである。読み手は、構文誤りを含むファイルを拒否しなければならない（MUST）。
  - 行末で文字列状態または指し手列状態にある行（閉じていない引用符や括弧）
  - RFC 8259 で認められないエスケープ、またはエスケープされていない制御文字を含む文字列
  - 9.4 の文法に合わない行
  - スキーマの属性の重複（下記）
- 属性は `キー=値` の形で、通常状態で最初に現れる `=` で分割する。属性のキーは、注釈キーの形（7.11。英小文字・数字・`_`・`-` からなる語を `.` で区切ったもの）で書く。`meta` 行のキーに限り、裸の語（半角英数字・`_`・`.`・`-` だけからなる語）か JSON 文字列で書く。
- 9.5 の表で欄に対応する属性（スキーマの属性）は、1行に同じキーを2回以上書いてはならない（MUST NOT）。
- 注釈に対応する属性は、同じ行に同じキーを複数書いてもよく（MAY）、その場合は書いた順が注釈の記録順となる。その行のスキーマの属性と同じキーを持つ注釈は、属性としては書けないので、`anno` 行で書かなければならない（MUST）。
- 値がない欄の属性は書かない。書き手は、値がない欄を `0` などで書いてはならない（MUST NOT）。
- 読み手は、行頭の半角空白を受け付けなければならず（MUST）、空行とメモ行の判定も行頭の半角空白を除いてから行う。書き手は行頭に空白を書いてはならない（MUST NOT）。

### 9.3 値の型

値の型は次の順で決める。

1. スキーマで型が決まっているキー（`edge` 行の欄、`engine` 行の欄、標準キーなど）は、スキーマの型で解釈する。たとえば `engine` 行の `version=9.00` は文字列である。
2. それ以外のキー（`x.` や `src.` で始まるキー）は、値の書き方で型を決める。

| 型 | 書き方 |
| --- | --- |
| 整数 | `-?[0-9]+`（先頭のゼロは書かない） |
| 実数 | 小数点か指数を含む10進数（例：`0.5`、`1e-3`）。有限の値に限る。書き手は NaN と無限大を書いてはならず（MUST NOT）、読み手は `nan`・`inf` などの表記を構文誤りとしなければならない（MUST） |
| 真偽 | `true` または `false` |
| 文字列 | JSON 文字列（RFC 8259）。型がスキーマで決まる文字列に限り、空白・`"`・`=`・`[`・`]` を含まなければ引用符を省いてもよい（MAY） |
| 指し手列 | `[` と `]` で囲んだ、半角空白区切りの USI 表記の指し手 |
| EVAL | スキーマで EVAL と決まる欄（`edge`・`prov`・`anls` の `eval`）でだけ使う。単位の値はそのまま整数で書き、詰みは `mate:+n` / `mate:-n`、手数不明は `mate:+?` / `mate:-?` と書く |

書き手は、型がスキーマで決まらないキーの文字列を、引用符で囲まなければならない（MUST）。

### 9.4 文法

空行とメモ行を除いた行の並びは、次の文法に従わなければならない（MUST）。

```
file       = header *rightsline [fileline] *source *engine *position *record
header     = "SPG-TEXT" SP "1.0" LF
rightsline = "rights" SP "id=" uint 1*(SP attr) LF
fileline   = "file" *(SP attr) LF *anno
source     = "source" SP "id=" uint 1*(SP attr) LF *anno
engine     = "engine" SP "id=" uint *(SP attr) LF *anno
position   = "pos" SP sfen3 *(SP attr) LF *anno *analysis *prov *edge
edge       = "edge" SP usimove *(SP attr) LF *anno *analysis *prov
prov       = "prov" SP "source=" uint *(SP attr) LF
analysis   = "anls" 1*(SP attr) LF *anno
anno       = "anno" SP attr *(SP "rights=" uint) LF
record     = "record" *(SP attr) LF *anno *meta root *analysis seq
meta       = "meta" SP mkey "=" string LF
root       = "root" SP ("startpos" / sfen3) *(SP attr) LF *anno
seq        = *(node / variation) [event *variation]
node       = ply SP usimove *(SP attr) LF *anno *analysis
event      = "event" SP eventname *(SP attr) LF *anno *analysis
variation  = "var" LF seq "end" LF
attr       = akey "=" value
akey       = word *("." word)
word       = 1*(%x61-7A / DIGIT / "_" / "-")
mkey       = barekey / jstring
barekey    = 1*(ALPHA / DIGIT / "_" / "." / "-")
```

- `sfen3` は正準 SFEN である。`startpos` は平手初期局面の正準 SFEN と同じ意味である。`jstring` は JSON 文字列、`string` は 9.3 の文字列型の値である。
- 木との対応：`seq` の中の `node` 行は、同じ `seq` の直前の `node` 行（なければ `seq` を含む構造の親：根、または `var` が変化させる手の親）の子である。`event` 行も同じ規則で親が決まり、子を持たない。
- `var` から `end` までは、その直前の兄弟（同じ `seq` で `var` の直前にある `node` 行または `event` 行）と同じ親を持つ別の子（変化）である。`var` の中の `seq` は空であってはならない（MUST NOT）。
- `ply` は根からの手数（最初の指し手が 1）で、親の手数 ＋ 1 でなければならない（MUST）。`event` 行の手数は、親の手数 ＋ 1 とみなす。`var` の最初の行の手数は、変化させる兄弟の手数と等しくなければならない（MUST）。
- `anls` 行は、直前の `pos`・`edge`・`root`・`node`・`event` 行（間の `anno` 行と `anls` 行は数えない）を対象とする解析結果である。
- `prov` 行は、直前の `pos` 行または `edge` 行を対象とする `PROV` のエントリである。`source=` は `source` 行の id を参照する。
- `anno` 行は、直前の `file`・`source`・`engine`・`pos`・`edge`・`anls`・`record`・`root`・`node`・`event` 行（間の `anno` 行は数えない）の対象への注釈1件を表す。`anls` 行の後の `anno` 行は、その解析結果エントリを対象とする（対象の種類8）。最初の属性がその注釈のキーと値であり、続く `rights=` は、その注釈を対象とする権利情報の注釈（対象の種類7）である。
- `eventname` は終局イベントの表の名前である。
- `rights`・`source`・`engine` 行の id は、行の種類ごとに 0 から始まり、出現順に 1 ずつ増えなければならない（MUST）。同じ種類で同じ id を2回定義してはならない（MUST NOT）。id を参照する属性（`rights`・`source`・`engine`）は、それより前の行で定義された id を参照しなければならない（MUST）。
- 属性 `rights=<id>` は、`rights` 行の id で権利情報を参照する注釈である。書ける行と意味は 9.5 の表による。`rights`・`engine`・`prov`・`meta` 行に書いてはならず（MUST NOT）、`engine` 行の後の `anno` 行の最初の属性にもしてはならない（MUST NOT）。anno 行の2番目以降の rights=（その注釈を対象とする権利情報、対象の種類7）は、engine 行の後を含むどの anno 行にも書ける。
- `meta` 行の値は常に文字列である。
- 属性の値がその欄の範囲（各節と付録E）を外れる行は構文誤りである。.spgt の読み手は、範囲外の値を丸めて受け入れてはならない（MUST NOT）。丸めを伴う値は、8.6 に従って丸めた値と src.range.\* の注釈で書く。
- edge 行と prov 行では、eval と engine は両方を書くか、両方とも書かないかのどちらかでなければならず（MUST）、depth は eval と engine があるときだけ書ける（MUST）。games・win・draw は3つそろえて書かなければならない（MUST）。これらに反する行は構文誤りである。

### 9.5 属性の対応

| 行 | 属性 | 対応する欄 |
| --- | --- | --- |
| `file` | 任意のキー | ファイル全体の注釈 |
| `rights` | `role`（`author` / `editor` / `source`）/ `name` / `copyright` / `license` / `license_text` / `url` / `date` | `RGHT` の各欄 |
| `source` | `name` / `uri` | `SRCS` の各欄 |
| `engine` | `name` / `version` / `unit`（`cp` / `winrate` / `raw`）/ `pawn` | `ENGN` の各欄 |
| `engine` | それ以外（`rights` を除く） | エンジンを対象とする注釈 |
| `pos` | `comment` など | 局面を対象とする注釈 |
| `edge` | `weight` / `eval` / `engine` / `depth` / `games` / `win` / `draw` / `disabled` | `EDGE` の各欄（`disabled` は真偽） |
| `prov` | `source` / `weight` / `eval` / `engine` / `depth` / `games` / `win` / `draw` / `disabled` | `PROV` の各欄 |
| `record` | `result`（`black` / `white` / `draw` / `unknown`）/ `start_ply` / `nongame`（真偽） | `RECS` の各欄 |
| `root`・`node`・`event` | `t` | 消費時間（ミリ秒） |
| `anls` | `engine` / `ctx`（`game` / `analysis` / `book`）/ `rank` / `eval` / `bound`（`exact` / `lower` / `upper`）/ `depth` / `seldepth` / `nodes` / `ms` / `winrate` / `pv` / `group` / `viewpoint`（`unknown`） | `ANLS` の各欄（`group` は探索の識別子、`viewpoint=unknown` は視点未確定） |
| `anls` | 上記以外のキー（`rights` を含む） | その解析結果エントリを対象とする注釈（対象の種類8） |
| `anno` | 最初の属性 | 直前の対象行の対象への注釈1件 |
| `anno` | 2番目以降の `rights` | その注釈を対象とする権利情報（対象の種類7） |
| `file`・`source`・`pos`・`edge`・`record`・`root`・`node`・`event` | 上記以外のキー（`rights` を含む） | その行の対象への注釈 |

属性を書かない欄は、次の既定値をとる。フラグで有無を表す欄（`eval`・`depth`・`weight`・`games`・`t`・`ms` など）は、属性がなければ「なし」である。

| 行 | 属性 | 既定値 |
| --- | --- | --- |
| `anls` | `ctx` | `game`。書き手は常に書くが、読み手は `ctx` のない `anls` 行を `ctx=game` として受け付けなければならない（MUST） |
| `anls` | `bound` | `exact` |
| `anls` | `rank` | 0（なし） |
| `anls` | `group` | 0（単独の結果） |
| `anls` | `viewpoint` | 視点確定 |
| `record` | `result` | `unknown` |
| `record` | `start_ply` | 0（不明） |
| `record` | `nongame` | `false` |
| `edge`・`prov` | `disabled` | `false` |

### 9.7 正準形

.spgt を書き出す書き手は、次の正準形で書かなければならない（MUST）。

1. 行の順序は、`header`、`rights`（id の昇順）、`file`（あれば）、`source`（id の昇順）、`engine`（id の昇順）、`pos`（`PKEY` の規定の順）、`record`（`RECS` の順）とする。`pos` の中の `edge` は `EDGE` の規定の順、`anls` は `ANLS` の順、`prov` は `PROV` の順とする。
2. 属性は、上の対応表に挙げた順に書き、その後に注釈を記録順に書く。次のいずれかに当たる注釈と、同じ対象でそれより後に記録された注釈は、属性ではなく `anno` 行で記録順に書く。
   1. 権利情報の注釈（対象の種類7）を持つ注釈
   2. キーがその行のスキーマの属性名と同じ注釈
3. 既定値（9.5）と等しい欄の属性は書かない。ただし `anls` 行の `ctx` は常に書く。
4. 数値は先頭のゼロを付けない10進数で書く。実数は、binary64 の値を最短で往復できる10進表記で書く。
5. 文字列とキーは、引用符を省ける場合は省き、省けない場合は必要最小限のエスケープで書く。
6. 空行とメモ行は書かない。行頭に空白を書かない。

## 10. 既存形式との変換

### 10.1 無損失性の段階

| 段階 | 要件 | 定義 | 実現手段 |
| --- | --- | --- | --- |
| L1 意味の無損失 | 取り込み器は満たさなければならない（MUST） | 元形式が表す情報（局面、指し手、分岐、消費時間、メタ情報とその順序、コメント、しおり、終局、結果、思考情報、定跡の各列）をすべて SPG から復元できる | 標準の欄とキー、`META`、`ANLS`、`src.*` |
| L2 表記の再現 | 取り込み器は満たすべきである（SHOULD） | 元形式へ書き戻したとき、表記上の選択（王/玉、▲△/▽、全角/半角、「同　」の空白など）も再現できる | `src.<形式>.*` に、既定の書き方と違う点だけを記録 |
| L3 バイト一致 | 取り込み器は満たしてもよい（MAY） | 元ファイルをそのまま取り出せる | `RAWS` に原本を格納 |

L1 を満たせないエントリがあるとき、取り込み器は取り込みを失敗させなければならない（MUST）。ただし利用者が部分取り込みを明示的に指定した場合は、続行してもよい（MAY）。続行した取り込み器は、欠けたエントリの件数と種類を呼び出し元に報告し、ファイル全体の注釈 `src.partial` に記録しなければならない（MUST）。

注記：原本を `RAWS` に残すことは L3 であり、L1 の代わりにはならない。

### 10.2 開始手数・結果・対局の記録かどうか

- 取り込み器は、元データの開始手数（SFEN の第4項目、BOD の「手数＝」など）を `RECS` の開始手数に保存しなければならない（MUST）。定跡の SFEN 行の手数は、注釈 `src.yane.ply` に保存しなければならない（MUST）。
- 取り込み器は、元データが勝敗を明示していればそれを結果としなければならない（MUST）。明示がなければ、本譜の最後のイベントから次の表で結果を決めなければならない（MUST）。
- 取り込み器は、元形式が対局の記録でないことを示す棋譜（詰将棋、定跡の手順など）について、`RECS` のフラグ bit1 を立てなければならない（MUST）。

| 本譜の最後のイベント | 結果 |
| --- | --- |
| 投了、時間切れ、反則（手番側の負け）、詰み、不戦（手番側の負け） | 手番側の負け |
| 反則（手番側の勝ち）、入玉宣言勝ち、不戦（手番側の勝ち） | 手番側の勝ち |
| 持将棋、引き分け、最大手数 | 引き分け |
| 千日手 | その局面が最初に現れてから4回目に現れるまでの間、一方の指し手がすべて王手であれば、その側の負け。そうでなければ引き分け。本譜で最後の局面が4回現れていない（記録が途中からなど）ときも引き分け |
| 中断、不詰、その他、イベントなし | 不明 |

取り込み器は、この仕様で表せない要素を含む棋譜を、L1 を満たせない入力として扱わなければならない（MUST）。すなわち、取り込みを失敗させるか、利用者が指定した場合に限り部分取り込みとして欠けた部分を報告する。待った（CSA の `%MATTA` など）は 8.5 の形で取り込まなければならない（MUST）。

### 10.3 形式ごとの写し方

この表は規範である。取り込み器は表の写し方に従わなければならない（MUST）。評価値の視点を「要検証」とした形式では、取り込み器はその評価値を視点未確定として格納しなければならない（MUST、8.1）。表にない項目は、取り込み器が判断して写してよく（MAY）、その場合は判断の内容を `src.<形式>.*` に記録すべきである（SHOULD）。

### 10.4 権利情報の取り込みと書き戻し

- 取り込み器は、元データの作者に関する項目（KIF・KI2 の「作者」、JKF の header の「作者」など）を、`META` に残したうえで、役割 = 作者の `RGHT` エントリとその棋譜の `rights` 注釈にも写さなければならない（MUST）。「発表誌」「出典」などの項目は、役割 = 提供元のエントリに写さなければならない（MUST）。
- 元データにライセンスの記載がないとき、取り込み器はライセンス式を `NOASSERTION` としなければならない（MUST）。取り込み器は、利用条件を推測して書いてはならない（MUST NOT）。
- 取り込み器は、利用者がファイル全体の権利情報（作者・編者・提供元・ライセンス・出典）を指定できるようにすべきである（SHOULD）。
- 書き戻し器は、元形式に作者や著作権を書く欄があれば、有効な権利情報をそこへ書くべきである（SHOULD）。書けない権利情報は、10.5 に従って警告しなければならない（MUST）。

### 10.5 書き戻し

書き戻し器は、元形式で表現できる範囲で書き戻す。表現できない情報（CSA への分岐、SFEN へのメタ情報など）を捨てるとき、書き戻し器は捨てた情報の種類を警告として呼び出し元に返さなければならない（MUST）。書き戻し器は、情報を黙って捨ててはならない（MUST NOT）。

## 11. 完全性と耐障害性

この章は、破損の検出、派生データの修復、更新の手順、改ざんの検出を定める。誤りの訂正はこの仕様の範囲外とし、ストレージ層の冗長化や再取得に任せる。

注記：想定する脅威と対策は次のとおりである。

| 脅威 | 例 | 対策 |
| --- | --- | --- |
| 偶発的な破損 | 保存媒体のビット化け、転送時の破損、mmap 中のメモリ上の反転（宇宙線など） | `CSUM`、アクセス時の妥当性検査、使用直前の再検証、メタデータの二重化、派生データの再生成 |
| 更新時の不整合 | 古いシャードと新しいマニフェストの混在、書き込み途中の停止 | ビルド ID、世代ごとのファイル名、マニフェストの原子的な置き換え |
| 意図的な改ざん | 配布された定跡に負け筋への誘導を混ぜる、細工したファイルで範囲外を読ませる | `BLK3`、マニフェストの署名、境界検査 |

### 11.1 ブロック

ブロックは、セクションを先頭から 65536 バイト（64 KiB）ごとに区切った各部分である。最後のブロックは短くてもよい。長さ 0 のセクションはブロックを持たない。

### 11.2 CSUM（ブロックチェックサム）

`CSUM` の対象は、長さが 64 KiB を超えるすべてのセクションのうち、`CSUM` と `BLK3` を除いたものである。書き手は、`CSUM` を次の配置で書かなければならない（MUST）。

| 部分 | 内容 |
| --- | --- |
| 前置部（64バイト、7.8） | 件数 = 対象セクション数、レコード長 = 24。固有欄の先頭にブロック長の log₂（u8、値は 16） |
| 対象表（1件24バイト、目録の順） | 種別タグ 4、予約 4、下段の配列内の先頭位置 u64、ブロック数 u64 |
| 下段 | 各対象の各ブロックの XXH3-64（seed = 0、u64）を、対象表の順に連結した配列 |
| 上段 | 下段の配列を 65536 バイト（8192件）ごとに区切った各部分の XXH3-64 の配列 |

目録の `CSUM` エントリのハッシュ欄には、前置部・対象表・上段をこの順に連結したバイト列の XXH3-64 を書かなければならない（MUST）。

読み手は、次のとおり検証しなければならない（MUST）。

1. ファイルを開くとき、目録の `CSUM` エントリのハッシュを検証する。
2. ブロック内のレコードを初めて使う前に、そのブロックのハッシュを下段と照合し、該当する下段の部分を上段と照合する。レコードが複数のブロックにまたがるときは、そのすべてを照合する。
3. 照合に失敗したブロックは破損として扱う。そのブロックが派生セクションに属するときは、再生成できることも報告する。

読み手は、照合に成功したブロックを記録し、2回目以降の照合を省いてもよい（MAY）。

読み手は、`CSUM` の対象外で長さが 64 KiB 以下の既知のセクションを使う前に、その内容を目録のハッシュと照合しなければならない（MUST）。照合に失敗したセクションは、全体を破損として扱わなければならない（MUST）。

注記：1兆局面規模で、下段は約13 GB、上段は約2 MB、照合済みのブロックを記録するビット表は約200 MB になる。

### 11.3 アクセス時の妥当性検査

読み手は、レコードを使う前に次を検査しなければならない（MUST）。違反を見つけた読み手は、そのレコードを含むブロックを破損として扱わなければならない（MUST）。

1. Move16 の条件（6.2）。
2. EVAL と勝率の値域（8.1）。
3. 予約の欄とビット（2.4）。
4. 局面のエッジ数が 593 以下で、エッジの範囲がエッジ表の中にあること。
5. `RNOD` の並びの規則のうち、そのノードについて検査できるもの（親までの距離の範囲など）。
6. フラグと欄の値の一致（`EDGE` などの規則）。

### 11.4 使用直前の再検証

エンジンは、定跡の手を対局で指す直前に、その局面の `POSN` とエッジを含むデータを、11.2 に従って `CSUM` または目録のハッシュ（64 KiB 以下のセクション）と再び照合し、指し手が合法であることを確認しなければならない（MUST）。照合に失敗したデータの手や合法でない手を、エンジンは指してはならない（MUST NOT）。大規模な定跡を常用する環境では、ECC メモリを使うべきである（SHOULD）。

注記：照合済みのブロックでも、その後にメモリ上で反転が起きうる。1手に1回の再検証の費用は数マイクロ秒である。

### 11.5 派生データと修復

派生データの内容は、元のデータと `KBKT` の b・s から一意に決まる。修復ツールは、派生データを元のデータから再生成してもよい（MAY）。

| 派生データ | 元のデータ |
| --- | --- |
| `KBKT` | `PKEY`、b、s |
| `PKEY` | `POSN` の CPE（拡張局面では正準 SFEN） |
| `POSN` のエッジの先頭位置 | 各局面のエッジ数 |
| `EDGE` / `EDGC` の子局面の添字 | 親局面に指し手を適用した局面の検索 |
| `OCCR` | 棋譜と局面表 |
| `CSUM`、`BLK3` | 各セクションの内容 |

注記：元のデータ（CPE、エッジの指し手と値、棋譜、注釈、解析結果、文字列、エンジン表、原本）が壊れたときは、バックアップから戻すか、マニフェストのハッシュで特定した同じファイルを再取得する。

### 11.6 メタデータの二重化

- 書き手は、目録の複製とヘッダの複製をファイル末尾に置かなければならない（MUST、7.1）。ヘッダの複製の「目録のオフセット」は目録の複製を指し、それ以外の欄は先頭のヘッダと同じでなければならない（MUST）。
- 読み手は、先頭のヘッダか目録の検証に失敗したとき、末尾の複製を検証したうえで使うべきである（SHOULD）。ヘッダの検証には、マジックとファイル長の照合に加えて、欄どうしの矛盾（ファイル種別とシャード番号など）の検査を含む。先頭のヘッダと目録が検証に通り、末尾の複製だけが食い違うときは、どちらが正しいか決められないので、読み手は破損として報告しなければならない（MUST）。BLK3 があれば、最初の葉と照合してどちらが正しいかを判定してよい（MAY）。
- 書き手は、マニフェストを `.spgm` と `.spgm.bak` の2つに書かなければならない（MUST）。更新を終えた状態では、両者は同じ内容でなければならない（MUST）。11.7 の手順の途中に限り、両者は異なる世代を指してよい（MAY）。
- 読み手は、次の順で使うマニフェストを選ばなければならない（MUST）。(1) `.spgm` の末尾の XXH3-64 が一致し、束ねるすべてのファイルが存在してそのヘッダのビルド ID が一致すれば、`.spgm` を使う。(2) そうでなければ `.spgm.bak` を同じ条件で検査し、満たせば `.spgm.bak` を使ってそのことを報告する。(3) どちらも満たさなければ、ファイル群を拒否する。

注記：11.7 の手順では古い世代のファイルを最後に消すので、更新の途中で止まっても、`.spgm` と `.spgm.bak` の少なくとも一方は、そろったファイル群を指す。

### 11.7 世代と更新の手順

書き手は、ビルドのたびに64bit の乱数でビルド ID を決め、全ファイルのヘッダとマニフェストに書かなければならない（MUST）。マニフェストで束ねるファイル群を更新する書き手は、次の順に従わなければならない（MUST）。

1. 新しいビルド ID の全ファイルを書き、永続化する（fsync など）。
2. 新しいマニフェストを一時ファイルに書いて永続化し、名前の付け替えで `.spgm` を置き換える。続いて `.spgm.bak` も同じ手順で置き換える。
3. 古いビルド ID のファイルを、それを開いている読み手がないことを確かめてから消す。確かめられないときは、消すのを遅らせるべきである（SHOULD）。

読み手は、11.6 の手順で選んだマニフェストのビルド ID と、束ねるファイルのいずれかのヘッダのビルド ID が一致しなければ、ファイル群を拒否しなければならない（MUST）。

### 11.8 改ざんの検出

注記：XXH3 は暗号学的ハッシュではない。`CSUM` が検出するのは偶発的な破損だけである。

**BLK3 の葉。** BLAKE3 は鍵なし・32バイト出力で用いる。葉の列は次のとおりである。

1. 最初の葉は、BLAKE3(`0x00` ‖ ヘッダ64バイト ‖ 目録) である。
2. 続いて、目録の順に、`BLK3` を除く各セクションの各ブロック B について、BLAKE3(`0x00` ‖ B) を並べる。

`BLK3` 自身、埋め草、末尾の複製は葉の対象外である。注記：`BLK3` の目録エントリ（オフセットと長さ）は最初の葉に含まれるが、`BLK3` の内容は含まれないので、循環は生じない。

**BLK3 の配置。** 前置部の件数は葉の数、レコード長は 32 で、前置部の後に葉を順に置く。

**Merkle 根。** 各段で左から2つずつ組み、BLAKE3(`0x01` ‖ 左 ‖ 右) を次の段の要素とする。段の要素数が奇数なら、最後の要素をそのまま次の段に上げる。要素が1つになったとき、それを根とする。

**署名。** マニフェストの署名欄（100バイト）は、方式（u8、1 = Ed25519）、予約3バイト、公開鍵32バイト、署名64バイトからなる。Ed25519 は RFC 8032 の Ed25519（pure）とする。署名の対象は、マニフェストの先頭から署名欄の直前までのバイト列である。

- 書き手が `BLK3` を書くときは、マニフェストの該当エントリにその根を書かなければならない（MUST）。書かないときは 0 を書く。
- 書き手がマニフェストに署名するときは、束ねるすべてのファイルに `BLK3` を含めなければならない（MUST）。
- 改ざんを検出しようとする読み手は、(1) マニフェストの署名を検証し、(2) 各ファイルの `BLK3` の葉から根を計算してマニフェストの値と比べ、(3) 使う各ブロックの BLAKE3 を葉と比べなければならない（MUST）。(1)〜(3) をすべて通ったブロックだけが、署名者の作成した内容と一致することが保証される。

署名のないマニフェスト、または信頼できない鍵で署名されたマニフェストでは、`BLK3` があっても真正性は保証されない。読み手は、そのようなファイル群を改ざん検出済みとして扱ってはならず（MUST NOT）、利用者に表示するときはその違いを示すべきである（SHOULD）。

注記：公開鍵をどう信頼するかは、この仕様の範囲外である。署名が保証するのは「誰が作ったか」と「その後変わっていないこと」までで、署名者自身が偏った定跡を作った場合は防げない。

**境界検査。** 読み手は、チェックサムや署名の結果にかかわらず、すべてのオフセット・添字・長さ・件数を、参照する前に範囲検査しなければならない（MUST）。範囲外の値を見つけた読み手は、その値を使って読んではならず（MUST NOT）、破損として扱わなければならない（MUST）。

**取り出し量の上限。** 多数の参照が同じ文字列や指し手列を指す細工でメモリを使い果たさないよう、読み手は、1つのファイルからデコードして取り出すデータの総量に上限を設けるべきである（SHOULD）。上限の目安は「ファイル長 × 8 ＋ 64 MiB」である。上限を超えた読み手は、そのファイルを拒否してよい（MAY）。

## 12. バージョニングと拡張

### 12.1 バージョン

- 既存の固定長レコードの配置、欄の意味、符号化を変える変更では、メジャーバージョンを上げなければならない（MUST）。
- セクション、注釈キー、値の型、フラグのビット、列挙値を追加する変更では、マイナーバージョンを上げなければならない（MUST）。マイナーバージョンの変更で、既存の欄の意味を変えてはならない（MUST NOT）。マイナーバージョンで追加するセクションに目録の bit0（必須）を立ててもよい（MAY）。注記：その場合、そのセクションを知らない読み手はファイルを拒否する。
- 読み手は、自身が知るメジャーバージョンより新しいファイルを拒否しなければならない（MUST）。自身が知るマイナーバージョンより新しいファイルは、bit0 の立った未知のセクションを含まなければ読まなければならず（MUST）、含めば拒否しなければならない（MUST）。知らない非必須の要素は、各章の規則に従って無視しなければならない（MUST）。
- 新しいマイナーバージョンのファイルで未知の列挙値（イベントコード、文脈、単位など）を見つけた読み手は、その値の意味を推測してはならず（MUST NOT）、その欄を「不明」として扱わなければならない（MUST）。エンジンは、意味を理解できない値（未知の単位の評価値など）を、定跡の手の選択に使ってはならない（MUST NOT）。
- マイナーバージョンで欄を追加するときは、既存の予約の欄に 7.9 の規則で置かなければならない（MUST）。予約の欄に収まらない追加は、新しいセクションか注釈キーで行うか、メジャーバージョンを上げて行う。

### 12.2 拡張

- 注釈キー `x.<提供元>.*` は、届け出なしで使ってもよい（MAY）。`<提供元>` は、ほかと重ならない名前（プロジェクト名やドメイン名）にすべきである（SHOULD）。
- 広く使われた拡張キーは、公開の登録簿で標準キーに昇格させる。読み手は、昇格の前に使われていたキーも受け付けるべきである（SHOULD）。
- 私用セクションの規則は 7.6 に従う。

## 13. 適合性と不変条件

### 13.1 適合性

- 適合する書き手は、次節の不変条件をすべて満たすファイルだけを出力しなければならない（MUST）。
- 適合する読み手は、下表のオープン時とアクセス時の検査を行わなければならない（MUST）。
- 適合する検証ツールは、下表の全件の検査を行わなければならない（MUST）。

| 段階 | 実施者と時機 | 検査内容 |
| --- | --- | --- |
| オープン時 | 読み手、ファイルを開くとき | マジック、バージョン、ファイル長、ファイル種別と必須セクション、各セクションの前置部（件数・レコード長と長さの整合）、目録のハッシュ（失敗時は末尾の複製）、`CSUM` の目録エントリのハッシュ、マニフェストとの整合（ビルド ID、シャード数、先頭局面の大域添字、キーの範囲） |
| アクセス時 | 読み手、レコードを使うたび | ブロックの `CSUM` 照合と、64 KiB 以下のセクションの目録ハッシュとの照合（いずれも初回）、アクセス時の妥当性検査、境界検査、引いた局面の CPE の復号と K の一致 |
| 全件 | 検証ツール | 上の検査をすべてのレコードに行い、加えて不変条件のすべて、`BLK3` と署名（あれば）、派生データと元のデータの一致、（厳格モードでは）すべての指し手の合法性 |

注記：エンジンが1兆局面のファイルを開くたびに全件を走査する必要はない。

### 13.2 不変条件

適合するファイル（マニフェストで束ねたファイル群では、その全体）は、次の条件をすべて満たさなければならない（MUST）。書き手はこれを満たさないファイルを出力してはならず（MUST NOT）、検証ツールはすべてを検査しなければならない（MUST）。

1. **正準性**：通常局面は 6.3 の手順どおりの CPE で、拡張局面は正準 SFEN で格納されている。
2. **キー**：`PKEY` の i 番目は、`POSN` の i 番目の局面の K に等しい。局面は規定の順に並ぶ。
3. **局面の一意性**：同じ局面は、ファイル群の中に1回だけ現れる。
4. **大域添字**：すべての大域添字は、総局面数（マニフェスト、単一ファイルではそのファイルの局面数）未満であるか、「なし」を表す全ビット 1 である。
5. **エッジ**：エッジは局面の順に隙間なく並び、各局面のエッジ数は 593 以下、指し手は互いに異なり、規定の順に並ぶ。
6. **子局面**：子局面の大域添字は、親局面に指し手を適用した局面がファイル群にあればその添字、なければ全ビット 1 である。
7. **欄とフラグ**：`EDGE`・`EDGC`・`ANLS`・`RECS`・`RNOD`・`POSN` の各欄の値は、フラグとの対応の規則を満たす。
8. **評価値**：評価値を持つエッジ、`EDGC`、`ANLS` は有効な `ENGN` を参照し、評価値と勝率はそれぞれの値域にある。
9. **棋譜**：`RNOD` は棋譜ごとに並びの規則を満たす。`RECS` の開始局面の大域添字は、その局面がファイル群にあればその添字、なければ全ビット 1 である。
10. **注釈と解析結果**：`ANNO` と `ANLS` は規定の順に並び、対象の添字は有効で、対象の「注釈あり」「解析結果あり」のフラグと一致する。
11. **文字列**：すべての文字列は正しい UTF-8 で、すべての文字列参照は `STRS` の中を指す。
12. **予約と埋め草**：予約の欄とビット、未定義のフラグのビット、埋め草はすべて 0 である。
13. **必須セクション**：ファイル種別ごとの必須セクションと、条件付きの必須セクションがそろっている。
14. **世代**：束ねるすべてのファイルのビルド ID は、マニフェストのビルド ID に等しい。
15. **完全性**：目録と `CSUM` のすべてのハッシュは内容と一致する。`BLK3` があれば、その根はマニフェストの値に等しい。
16. **二重化**：末尾のヘッダと目録の複製は、規定どおり先頭のものと同じ内容である。
17. **権利情報**：すべての rights 注釈の値は RGHT の有効な添字である。ファイル全体を対象とする権利情報は、束ねるすべてのファイルで同じである。
18. **注釈の対象**：対象の種類7・8の注釈は 7.19 の制限を満たし、対象の種類9の注釈の添字は SRCS の中を指す。
19. **由来情報**：PROV は規定の順に並び、同じ対象と出典の組は1件だけである。出典ごとの勝敗統計を持つエッジの統計は、PROV の和に等しい。統合した局面・エッジの有効な権利情報は、寄与した出典の権利情報の和集合である。
20. **前置部**：すべてのセクションは前置部で始まり、既知のセクションのレコード長は 7.8 の値に等しく、件数・レコード長・セクションの長さは整合する。

## 付録A 規模とコストの見積もり（参考）

この付録の数値は見積もりであり、要件を定めない。

### A.1 1兆局面での容量

| セクション | 1件 | 1兆局面での大きさ |
| --- | --- | --- |
| `PKEY` | 8 B | 8 TB |
| `POSN` | 48 B | 48 TB |
| `EDGE`（完全形） | 48 B | 48 TB |
| `EDGC`（簡易形） | 16 B | 16 TB |
| `KBKT`（s = 8、b = 16） | 8 B × (2¹⁶ ＋ 1) × 2⁸ | 128 MiB |

エッジ数が局面数とほぼ同じと仮定すると、合計は完全形で約104 TB、簡易形で約72 TB である。1台のディスクに収まらない規模なので、シャード分割を前提とする。

### A.2 完全性のための追加容量

| 対策 | 追加容量 |
| --- | --- |
| `CSUM`（64 KiB ごとに 8 B） | 約13 GB |
| 照合済みのブロックを記録するビット表（メモリ） | 約200 MB |
| ヘッダ・目録・マニフェストの二重化 | 数 KB |
| `BLK3`（64 KiB ごとに 32 B） | 約51 GB |
| 署名 | 100 B |

### A.3 由来情報の追加容量

`PROV` は、出典が2つ以上のときだけ必要になる。容量は「寄与の数 × 64 B」である。例えば 1兆局面・局面あたり平均 1.5 本のエッジを持つ定跡を、平均 2 出典から統合した場合、局面とエッジあわせて約 5×10¹² 件の寄与となり、約 320 TB を要する。この大きさが問題になる用途では、統合後の配布用ファイル群と、`PROV` を含む保存用ファイル群を分けることが考えられる。ただし、配布用ファイル群でも統合したデータの権利情報は保たなければならず（8.3）、`PROV` を省く場合は 8.4 の指示と `merge.rule` の記録が必要である。

## 付録D v1.0 で決めた事項と将来の検討事項

この付録は参考である。D.1 の決定は、本文の該当節に規範として書いてある。

### D.1 v1.0 で決めた事項

- **手数依存の定跡**：局面グラフには入れない。やねうら王の手数を区別する運用は、`src.yane.byply` に原文で保持するだけとする（10.3）。
- **シャードとバケット**：局面シャードに分割するときは s = 8、分割しないときは s = 0 とし、b = 16 とする（7.15、7.28）。
- **CPE を省く縮小形式**：採用しない。局面は常に CPE（拡張局面では正準 SFEN）で照合する。
- **圧縮**：.spg そのものは圧縮しない。配布用の圧縮は、形式・手法・拡張子を問わない（7.29）。
- **待った**：取り消された手順を変化とし、その末尾に待ったのイベント（コード 13）を置く（8.5）。
- **評価値の視点**：Floodgate／CSA V3、ShogiGUI、ShogiHome の評価値は、視点が実データで確かめられるまで視点未確定として格納する（8.1、10.3）。
- **名称と拡張子**：名称を SPG、拡張子を .spg・.spgt・.spgm とする。
- **追記**：v1.0 のファイルは一括で書く。内容を変えるときは新しいビルドを作る（11.7）。
- **KFLT**：予約のタグとし、v1.0 では書かない（7.7）。
- **棋譜専用ファイル**：マニフェストあたり高々1つとする（7.28）。
- **対象外**：中将棋・5五将棋などの変則将棋、千日手の履歴に依存する評価、学習データ形式（psv、hcpe など）の置き換え。

### D.2 将来の検討事項（v1.0 の範囲外）

- **KFLT の形式**：存在フィルタ（Binary Fuse など）の内部形式を、相互運用できる粒度で規定する。
- **複数の棋譜専用ファイル**：大規模な棋譜集を分割する方法。
- **追記ログと統合**：一括ビルドを補う追記と統合（compaction）の手順。
- **評価値の視点の写し方**：実データで視点を確かめた形式の写し方を、マイナーバージョンで定める。
- **学習データとの相互変換**：CPE と psv・hcpe の相互変換。

### E.6 表せないもの

次のものは v1.0 では表せない。取り込み時には、10章に従って取り込みを失敗させるか、部分取り込みとして欠けた部分を報告する。

- 9×9 以外の盤や、本将棋にない駒を使う変則将棋（中将棋、5五将棋など）。
- パス（何も動かさない手）や、1手で複数の駒を動かす手。
- 手数や手順の履歴で局面を区別すること（千日手の判定、手数別の定跡）。手数別の情報は `src.yane.byply` の原文としてだけ残る。
- 左右反転・先後反転した局面の同一視。
- 1局面に 593 を超える候補手。拡張局面で合法手が 593 を超えても、エッジにできるのは 593 本までである。
- 65,535 手を超える読み筋・指し手列、ノード数が 2³² − 1 を超える1つの棋譜。
- 手数が 65,535 手を超える詰みの正確な手数（手数不明の詰みとしては表せる）。
- ミリ秒より細かい時間と、約49.7日を超える1手の消費時間・思考時間。
- 単位をそろえた評価値の換算（単位が異なる評価値はそのまま保持し、比較しない）。
- 型付きの日時。対局日時などは `META` や注釈の文字列として持つ。
- Ed25519 以外の署名方式。
